# ADR-0005: PR 自動レビューの起動イベントを pull_request_target にする

- 状態: accepted
- 日付: 2026-09-14
- 関連: [ADR-0002](0002-pr-ai-review.md)（その「影響」節の `pull_request_target` に関する記述を訂正する）

## 背景

PR #1 に対する AI 自動レビュー自身が、このワークフローに critical のセキュリティ指摘を出した。

`on: pull_request` は、**同一リポジトリのブランチから作られた PR では PR 側のワークフロー定義を
実行する。** そこに `OPENAI_API_KEY` を渡しているため、このリポジトリに push できる人は
PR 内でワークフローを書き換えてシークレットをログや外部サービスへ送信できる。
フォークを除外しても防げない。

この挙動は PR #1 自身で実証されている。`package-manager-cache: false` の修正を PR ブランチへ
push しただけで `review` ジョブが成功した。`main` に入っていない PR 側の定義が実行された、
ということである。

ADR-0002 には「外部からの貢献を受けるようになったら `pull_request_target` は使わず、
メンテナによる手動実行で運用する」と書いた。**この記述は不正確だった。**
フォークからの貢献だけを想定しており、同一リポジトリの PR からシークレットを抜ける
この経路を扱っていない。

## 選択肢

| 案 | 内容 | 欠点 |
| --- | --- | --- |
| A | `pull_request_target` に変更する | 将来 PR のコードを checkout した瞬間、シークレット付きで任意コードを実行する深刻な穴になる |
| B | 現状維持。リスクを文書化するのみ | 1 人開発の間は実害がないが、共同作業者を追加した時点で現実の穴になる。移行を忘れるリスクが残る |
| C | キーを GitHub Environments の保護ルール配下に置く | 確実だが PR ごとに手動承認が必要で、自動レビューの利点が大きく損なわれる |
| D | 自動実行をやめ `workflow_dispatch` のみにする | 毎回手で起動する手間がかかる |

## 決定

**A を採用する。** `pull_request_target` はワークフロー定義とスクリプトを常にベースブランチから
読むため、PR 側から書き換えられない。

A の欠点（PR のコードを checkout すると危険）は、**このワークフローに限っては構造的に生じにくい。**
差分は GitHub API から取得しており、PR のコードを取得する必要がそもそもない。
そのうえで、将来うっかり `ref` を足さないよう、ワークフローに警告コメントを置いた。

フォークからの PR を対象外にする条件はそのまま残す。`pull_request_target` ならフォークの PR も
安全にレビューできるが、現時点で必要がなく、対象を広げる判断は別途行う。

## 影響

- **この変更は `main` にマージされるまで効かない。** `pull_request_target` はベースブランチの
  ワークフロー定義で起動するため、`main` にこのファイルが無い間は起動しない。
  PR #1 自身では AI レビューはもう走らず、マージ後の次の PR から有効になる。
- ワークフローの `checkout` には `persist-credentials: false` を付けた。
  ベースブランチのファイルを読むだけで、git 認証情報を残す必要がないため。
- **ワークフローの変更が PR 上で検証できなくなる。** ベースブランチの定義が使われるので、
  以後この自動レビューのワークフローを変更する場合は、マージするまで実際の挙動を確認できない。
  変更は小さく保ち、スクリプト側のロジックはテスト（`.github/scripts/ai-review.test.mjs`）で
  担保する。
- CI（`.github/workflows/ci.yml`）は `pull_request` のまま。シークレットを使わないため
  この経路の影響を受けない。

## 覆すとしたら

- フォークからの PR もレビュー対象にしたくなったとき → 条件を緩める判断を別 ADR で行う
  （`pull_request_target` のままで対応できるが、外部から来た差分をそのままモデルへ送ることの
  是非を改めて検討する）
- GitHub が `pull_request` でシークレットを安全に扱う仕組みを提供したとき
