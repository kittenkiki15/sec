# ADR-0013: 非有限値は値として持たず、`#Overflow` を F-8-2 に足す

- 状態: accepted
- 日付: 2026-09-14
- 関連: 要件 F-8-2、[ADR-0012](0012-number-model.md)、仕様書 §0.3、§6.1

## 背景

ADR-0012 は数を**任意精度の整数**と**IEEE754 倍精度の小数**の 2 種と定めた。
しかし**整数を小数へ変換できない場合の規則を定めていなかった。**

```smalltalk
1e400 / 3     "10^400 は整数として持てるが、商は小数が要る。倍精度では表せない"
1e400 + 0.0   "混在演算。同じく変換できない"
1.0e308 * 10  "小数どうしでも範囲を超える"
```

IEEE754 に従えば `Infinity` になるが、**この仕様書は既に 2 回、非有限値を拒んでいる。**

| 式 | IEEE754 なら | 本仕様 |
| --- | --- | --- |
| `1 / 0` | `Infinity` | `#DivideByZero` |
| `-1 sqrt` | `NaN` | エラー |

さらに §6.1 は `rounded` / `truncated` が**常に整数を返す**と定めており、
`Infinity` を値として認めるとこの規則が成り立たなくなる。PR #11 の AI レビューが
この矛盾を指摘した。

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | エラーにする。既存の `#TypeError` を使う | 変更が仕様書の中で閉じる | 「型の誤り」という名前で範囲の誤りを表すことになり、読み手に伝わらない |
| B | エラーにする。**F-8-2 に `#Overflow` を足す** | 名前が原因を正しく表す。Excel の `#NUM!` に相当 | **要件定義書の変更**を伴う。既存フィクスチャの期待値が 1 件変わる |
| C | `Infinity` を小数の値として認める | IEEE754 に忠実 | §0.3 に表記が増え、**`rounded` / `truncated` の規則を作り直す**必要がある。`1 / 0` を `#DivideByZero` とした既定ともちぐはぐ |

## 決定

**B を採用する**（利用者の選択）。

- **非有限値（`Infinity` `NaN`）は値として存在しない。** よって `rounded` / `truncated` が
  常に整数を返す規則はそのまま保たれる
- **F-8-2 のエラー種別に `#Overflow` を足し、8 種とする。** 表すのは
  **数の範囲・定義域の誤り**であり、オーバーフローだけではない
- **`-1 sqrt` を `#TypeError` から `#Overflow` へ移す。** 定義域の外という同じ理由なので、
  1 つの種別にまとめる

### 変換は演算より先に起きる

**小数が必要になった時点で、被演算子を小数へ変換する。** 結果を正確に求めてから
変換するのではない。

```smalltalk
1e400 sqrt    "→ #Overflow。結果の 1e200 は表せるが、受け手の変換が先"
1e400 / 3     "→ #Overflow"
```

結果側で判断する方式（正確な有理数を経由してから変換する）なら `1e400 sqrt` は
`1e200` を返せるが、それは内部に分数を持つことに等しく、ADR-0012 が案 B として
退けたものになる。**規則を 1 つに保つ方を採った。**

### ただし、演算の成否の検査より先ではない

「変換が先」が指すのは**結果の表現を決める段階**であって、その演算が成り立つか
どうかの検査を飛び越すものではない。

```smalltalk
1e400 / 0.0   "→ #DivideByZero。#Overflow ではない"
```

検査の順序は §6.0 に表で置いた。**受け手がセレクタを持つか → 引数の型 →
演算が定義されるか → 結果を表せるか**の順で、`#DoesNotUnderstand` を `#TypeError` より
先に置いた §6.0 の並びをそのまま延長したものである。「その演算が成り立つか」を先に、
「値を表せるか」を後に見る。

この区別は当初の記述では曖昧で、PR #11 の AI レビューが 2 通りに読めることを指摘した。

### 桁が落ちるのはエラーにしない

**変換できる範囲での精度の損失は、エラーではない。**

```smalltalk
9007199254740993 + 0.0   "→ 9007199254740992.0。2^53 + 1 は倍精度で表せない"
9007199254740993 + 1     "→ 9007199254740994。整数どうしなら正確"
```

倍精度を選んだ時点で受け入れた帰結であり、ADR-0012 が `0.1 + 0.2` を隠さないと
決めたのと同じ理由による。**エラーにするのは「表せない」場合だけで、
「精度が落ちる」場合ではない。**

## 影響

- **要件定義書 F-8-2 を変更する。** エラー種別が 7 種から 8 種になる
- §0.3 のエラー種別の列挙と、§6.1 の `sqrt` の行を更新する
- **`tests/golden/numbers.txt` の `-1 sqrt` の期待値が変わる。**
  ゴールデンテストの期待値の変更は仕様変更であり、その根拠が本 ADR である
- ADR-0012 は覆らない。**本 ADR はその欠けていた部分を埋めるものである**
- 評価器は、整数から小数への変換点で有限性を検査する必要がある

## 覆すとしたら

- `#Overflow` という名前が、定義域の誤り（`-1 sqrt`）を含むことと合わないと判明したとき
  → `#NumError` などへの改名を検討する。**種別を増やすのではなく名前を変える**
- 大きな数の `sqrt` が実務で必要と分かったとき → 結果側で判断する方式を再検討する。
  ただし ADR-0012 の案 B（分数）と地続きの選択になる
