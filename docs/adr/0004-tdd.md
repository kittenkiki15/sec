# ADR-0004: テスト駆動開発を標準の進め方とする

- 状態: accepted
- 日付: 2026-09-14

## 背景

M0.5 までの規約では、テストを先に書くことは `tests/golden/*.txt` についてのみ明記されており、
一般則としては定めていなかった。実際、M0.5 で作ったゴールデンテストのハーネス自身は
実装を先に書いてからテストを付けている。

1 人 + Claude Code という体制では、この曖昧さが具体的な害をもたらす。

1. **テストが実装のスナップショットになる。** 実装を先に書くと、テストは
   「仕様どおりか」ではなく「今の実装がこう振る舞うこと」を固定するものになりやすい。
   実装を書いたのが AI であれば、その誤りごと固定される。
2. **AI に渡す完了条件が曖昧になる。** 「◯◯を実装して」は判定基準が人間の目視だが、
   「このテストを緑にして」は Claude 自身が判定できる。開発方針の中核である
   「Claude が自分で正誤を判定できるループ」は、テストが先にあって初めて成立する。
3. **レビューの負荷が下がらない。** テストが先にあれば、人間は実装 300 行ではなく
   テスト 30 行を読んで仕様の妥当性を判断できる。

## 選択肢

| 案 | 内容 | 欠点 |
| --- | --- | --- |
| A | 全面的に TDD を標準とする（明示的な例外つき） | 探索的な作業とは相性が悪い。例外を明示しないと形骸化する |
| B | ゴールデンテストのみ TDD（M0.5 までの現状） | 言語仕様以外のコード（シートモデル、依存グラフ、CLI、MCP）が野放しになる |
| C | テストは必ず書くが順序は問わない | 上記 1〜3 の問題がそのまま残る |

## 決定

**A を採用する。振る舞いを変えるコードは、失敗するテストを書いてから実装する。**

サイクルは Red → Green → Refactor とし、**Red の確認を省略しない。**
落ちることを確認していないテストは、仕様を検証している保証がない
（対象を間違えている、常に真になっている、といった欠陥が見えない）。

### 適用範囲

**プロダクトコードだけでなく、CI やツールのスクリプト（`.github/scripts/` 配下など）も対象とする。**
「設定ファイル」の例外に含めない。振る舞いを持つコードである以上、扱いを変える理由がない。

この線引きは実例で裏づけられている。`ai-review.mjs` の差分上限のバグ
（上限直前で 1 ファイル分を超過して送信する）は、この方針に従ってテストを先に書いたことで
`expected 180 to be less than or equal to 100` として再現し、発見できた。
ツールだからと例外にしていれば見逃していた。

`.github/scripts/**/*.test.mjs` は `vitest.config.ts` の対象に含めてある。

### 例外

次に限り、テストを先に書かなくてよい。**例外は広げない。**

| 例外 | 条件 |
| --- | --- |
| 探索的スパイク | 捨てる前提の試作。**本実装は必ず TDD で書き直す。** スパイクをそのまま残さない |
| 性能ベンチマーク | 計測が目的で、合否判定が無いもの |
| UI の見た目の調整 | 振る舞い（状態遷移・入出力）を変えないもの |
| 機械的なリファクタリング | 既存テストが振る舞いを担保しており、それが緑のまま通ること |
| 設定ファイル・ドキュメント | — |

## 影響

- **実装を依頼されたら、まずテストを書き、落ちることを示してから実装に進む。**
  Claude Code は「テストを書いた」「落ちることを確認した」を明示的に報告する。
- **バグ修正も同じ。** 先にそのバグを再現する失敗テストを書く。
  再現しないテストを書いて修正しても、直ったことの証明にならない。
- **git 履歴でテストを先のコミットに置く。** 差分だけを見ても「先に書いたか」は分からないため、
  履歴がその唯一の証拠になる。1 コミットにまとめる場合は、コミット本文にその旨を書く。
- PR 自動レビュー（`.github/ai-review-guidelines.md`）は、
  振る舞いの変更にテストが伴わない差分を指摘する。

### 検証できること・できないこと

差分からは「テストを先に書いたか」は判定できない。検証できるのは次の 2 点であり、
規約はこれを根拠に運用する。

- 振る舞いを変える差分にテストが伴っているか
- テストが実装のスナップショットになっていないか
  （実装の出力をそのまま期待値に写したように見えるもの、
  実装を消しても落ちないテスト、境界値・エラーケースの欠落）

## 覆すとしたら

- 探索的な性格の強いパッケージ（UI の試作など）で例外の適用が常態化し、
  規約が形骸化したとき → そのパッケージだけ別の基準を定める ADR を起こす
