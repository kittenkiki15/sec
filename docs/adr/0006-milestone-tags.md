# ADR-0006: マイルストーンのタグ付け

- 状態: accepted
- 日付: 2026-09-14

## 背景

マイルストーンを完了するたびに、その時点のリポジトリを後から辿れるようにしたい。
M0.5（リポジトリ基盤）の完了時にこの必要が生じた。

## 決定

### 命名規則

**`m<マイルストーン番号>`**（例: `m0.5` / `m1` / `m3.5`）。

- 要件定義書の M0.5 / M1 という表記とそのまま対応する。
- 将来 MVP をリリースするときの `v0.1.0` 形式と明確に区別できる。
- 番号の先頭に 0 は付けない（`m01` と `m1` が別のタグとして並ぶのを避けるため）。

### 形式

**注釈付きタグ（annotated）**とし、併せて **GitHub Release** を作る。
軽量タグにしないのは、作成日時・作成者・メッセージが残り `git describe` でも扱いやすいため。
Release を作るのは、Releases ページに「各マイルストーンで何ができたか」が一覧で残るため。

### 作成手段

**GitHub Actions のワークフロー（`.github/workflows/tag-milestone.yml`）から作る。**
Actions 画面の "Run workflow" で、タグ名・タイトル・本文・対象コミットを入力する。

手元の git から直接 push しないのは、**開発セッションの egress ポリシーがタグ ref の
push を許可しない場合があるため**。M0.5 のタグ付けで実際にこれに当たった。
ブランチの push は通るのにタグの push だけが HTTP 403 で拒否される、という状態だった。
ワークフローは Actions の中で `GITHUB_TOKEN` を使って動くため、この制約を受けない。

副次的な利点として、タグ名の検証（`.github/scripts/validate-milestone-tag.mjs`）を
必ず通すことになり、規則に合わない名前や既存タグの上書きを防げる。

## 影響

- タグは Actions 画面から作る。手元で `git tag` して push する運用は取らない。
- タグ名の検証は規則に沿っているかを機械的に確認する。規則を変える場合は
  この ADR と `validate-milestone-tag.mjs` の両方を直す（テストが規則の実体）。
- ワークフローの入力は `env` 経由で渡し、`run` に直接埋め込まない。
  スクリプト注入の余地を作らないため。
- **タグの上書きはしない。** 既存のタグ名を指定した場合は既定で失敗する。
- ただし、タグの push は Release 作成より先に完了するため、Release 作成だけが失敗すると
  「タグはあるが Release が無い」状態が残る。既存タグを一律に拒否するとこの状態から
  復旧できなくなるため、**復旧専用の入力 `allow_existing_tag` を用意した。**
  これを true にすると、タグを作り直さずに Release だけを作成する。
  既定で受け入れないのは、打ち間違いで既存のタグ名を指定したときに
  意図しないコミットへ Release が付くのを防ぐため。
- 何を作るかの判断は 4 通りに分岐するため、shell ではなく
  `.github/scripts/decide-tag-action.mjs` に切り出してテストで担保している。

## 覆すとしたら

- 開発セッションからタグを push できるようになったとき → 手元から打つ運用に戻してもよいが、
  検証を通す利点は残るのでワークフローを使い続ける判断もありうる
- MVP をリリースして `v` 系のタグを併用するようになったとき → 命名規則を再検討する
