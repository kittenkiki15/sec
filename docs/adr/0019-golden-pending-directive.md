# ADR-0019: ゴールデンテストのケースを保留にする記法

- 状態: accepted
- 日付: 2026-09-15
- 関連: [ADR-0003](0003-golden-test-format.md)（形式）/ [ADR-0009](0009-golden-sheet-directives.md)（シートディレクティブ）/ [ADR-0018](0018-golden-macro-directive.md)（マクロのディレクティブ）/ [ADR-0006](0006-milestone-tags.md)（マイルストーンのタグと Release）

## 背景

M2（評価器 + CLI）の完了条件は「**セル参照なしの式**が評価できる。ブロック・条件・
コレクション操作が動作」（要件定義書 §8）。セル参照は M3、マクロは M4 である。

**フィクスチャ 712 件のうち 166 件は、M2 では原理的に緑にならない。**

| 区分 | 件数 | 必要なもの |
| --- | --- | --- |
| M2 で緑にする | 546 | 評価器 |
| M3 待ち | 106 | シートモデル（セル参照・シート指定・名前付き範囲） |
| M4 待ち | 60 | マクロ |

**この 166 件はファイル内に混在している。** `collections.txt` は 109 / 46 で割れ、
`errors.txt` は 19 / 10 で割れる。§6.3 が `Array` と `Range` を同じ節で定めており、
エラーの伝播順序はセル参照を絡めた形でも固定されているためで、**ファイル単位の選択では
切り分けられない。**

切り分ける手段が無いと、ゴールデンテストは M4 が終わるまで赤のままになる。
**赤が既定の状態になると、新しく壊れたことに気付けない。** M2 の 546 件が緑を保っている
ことこそ、各段階で確かめたいことである。

**もう 1 つ、リポジトリの外から見える目的がある。** マイルストーンの完了時にはタグと
併せて GitHub Release を作る（[ADR-0006](0006-milestone-tags.md)）。
**Release を入手した人が、その時点で言語仕様のどこが実装済みでどこが未実装かを
判別できなければならない。** `tests/golden/*.txt` は言語仕様の実体であり、
Release の利用者にとっては「この処理系が何をできると謳っているか」の一覧でもある。
**実装されていないケースがそれと分かる形で入っていないと、仕様書が実態より広く読める。**

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | ケースに `!pending <マイルストーン>` の印を置く | 判定が原文に書いてあり、読めば分かる。**Release を入手した人にも実装状況が伝わる。** ケースごとに独立。既存のディレクティブと同じ姿 | 印を外す作業が要る |
| B | AST から機械的に判定する（セル参照・自由な識別子・`!macro` を含むケースを外す） | フィクスチャを一切触らない。M3 で条件を緩めれば自動で対象が増える | 判定が原文から見えない。**Release を入手した人には実装状況が伝わらない。** **ブロック引数と自由な識別子の区別**など、判定器自体が誤りうる |
| C | 保留リストを `file:line` で別に持つ | フィクスチャを触らない。Release からも読める | **フィクスチャを編集するたびに行番号がずれる。** ケースの追加が保留リストの書き換えを呼ぶ。ケースと印が離れており、突き合わせないと読めない |
| D | ファイル単位で対象を選ぶ | 仕組みが要らない | `collections.txt` と `errors.txt` が割れる。**切り分けられない** |

## 決定

**案 A。ケースに `!pending <マイルストーン>` を置き、そのケースが緑になるマイルストーンを書く。**

```text
"セル参照は M3 から
!pending m3
!A1 := 1
A1 + 1
=> 2

"マクロは M4 から。!macro の次に置く
!macro
!pending m4
| a |
a := 3.
^ a
=> 3
```

### 保留のケースが通ってしまったら失敗にする

**これがこの案の要点である。** 保留のケースは落ちても失敗にしないが、
**期待値と一致したら失敗として報告する。**

黙って見逃すと、**「まだ保留」と「印を外し忘れた」が区別できなくなる。** 外し忘れた印は
そのケースを永久に検査の外へ置き、網羅の穴として残る。`tests/golden/selectors.mjs` が
「解析できないケースは `#Syntax` を期待していることを確かめてから飛ばす」としたのと同じ理由で、
**飛ばす判断そのものを検査の対象にする。**

失敗の報告には印を外す指示を添える（`"!pending m3" の印を外してください`）。

### マイルストーン名を検証する

`m0` / `m0.5` / `m1` … の形（[ADR-0006](0006-milestone-tags.md) のタグと同じ綴り）だけを
受け付ける。**`!pending m33` のような綴りの誤りを黙って通すと、どのマイルストーンでも
外されない印になる。**

### 置く位置

**`!macro` の次、セルの指定より前。1 ケースに 1 つだけ。** 位置を 1 箇所に固定するのは、
ADR-0009 が「同じことに 2 通りの書き方を作らない」としたのと同じ理由である。
読む側が、シートの準備を読む前に「このケースは保留」と分かる順でもある。

### 案 B を採らなかった理由

**決め手は Release である。** 判定器はリポジトリの中でしか動かない。Release を入手した人が
`tests/golden/*.txt` を読んだとき、どのケースがその版で通るのかが原文から分からない。
**印を原文に置けば、フィクスチャだけで完結して読める。**

そのうえで、**判定器は誤りうる。**

最初に書いた判定器は `[:x | x * 2] value: 3` を「識別子 `x` を含むからセル参照が要る」と
誤判定した。**ブロック引数は束縛されていて、セル参照ではない。** 7 件が M2 の対象から
静かに漏れていた。判定が原文に現れていれば、フィクスチャを読む側がこの誤りに気付ける。

**判定器を使い捨てにし、結果を原文に焼き付けた**のが本 ADR の形である。
印が原文にあれば、この誤りは Release の利用者にも見える形で残る。

## 影響

- `GoldenCase` に `pending: string | null` が増えた。印の無いケースは `null`。
- `GoldenInput` は変えていない。**評価器には保留かどうかを渡さない。** 評価に関係せず、
  評価器が「保留だから手を抜く」経路を作りたくない。
- `runGoldenCases` は、保留のケースが落ちても例外で終わっても失敗に含めない。
  **一致したときだけ失敗に含める。**
- 次はエラーにする。**`!macro` より前・セルの指定より後に置かれた `!pending`**、
  **重複**、**マイルストーン名が無い／形でないもの**、**`!pending` だけで式が無いケース**。
- `tests/golden/README.md` と `CLAUDE.md` のゴールデンテストの節に書き方を足した。
- 166 件に印を付けた（`m3` が 106 件、`m4` が 60 件）。**期待値は 1 件も変えていない。**
- **マイルストーンを完了して Release を作るときは、その印を外してから作る。**
  `m3` の Release に `!pending m3` が残っていれば、実装済みのものが未実装に見える。
  外し忘れはハーネスが赤にして知らせる。

## 覆すとしたら

- M4 が終わって印が 1 つも残らなくなったとき → 記法ごと外す。
  **ハーネスに残しておく理由は無い**（残せば、次に「とりあえず保留にする」使い方を招く）
- 保留の理由がマイルストーンで言えなくなったとき（環境差など）→ 理由を書ける形に変える
