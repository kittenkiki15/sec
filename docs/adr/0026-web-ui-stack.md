# ADR-0026: Web UI の構成（React + Vite、テストは happy-dom）

- 状態: accepted
- 日付: 2026-09-18

## 背景

M3.5（動くデモ）で `packages/web` を作る。**このリポジトリで初めてブラウザで動くコードを書く**ので、
UI の作り方・ビルド・テストの回し方を決める必要がある。

ADR-0001 はビルドについてだけ「`web` を作る段階で Vite のビルドを足す」と先送りしていた。
**UI の作り方とテストの回し方は誰も決めていない。**

制約は 3 つある。

- **TDD が必須**（ADR-0004）。UI にも Red を先に出せる形が要る。「UI の見た目の調整」の例外は
  振る舞いを変えないものに限るので、**セルを編集すると下流が再計算される**のような振る舞いは例外に当たらない
- **要件 N-3 は初回ロードを 500KB gzip 以内**と定める
- **要件 N-7 は Chrome / Firefox / Safari の最新 2 版**で動くこと

M3.5 は縦切りだが、**ここで採る構成は M6（本番の Web UI）にそのまま効く。** M3.5 を
「捨てる前提の探索的スパイク」（ADR-0004 の例外）にはしない——要件定義書 §8 が M3.5 を
マイルストーンとして置いているのは、**UX の前提を早期に検証する**ためであり、
検証した形を捨てるなら検証にならない。

## 選択肢

### UI の作り方

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | 素の DOM API のみ | 依存が増えない。N-3 に最も余裕が出る | 100 セルの差分更新を手で書くことになる。M6 の数式バー・補完・マクロエディタで破綻しやすい |
| B | React | M6 まで見据えた形を最初から確かめられる。周辺（テスト用の道具・知見）が最も厚い | 依存とバンドルサイズが増える（gzip 約 45KB） |
| C | 軽量フレームワーク（Preact / Solid） | 宣言的でバンドルが小さい | 採用例が少なく、判断材料が要る |

### DOM を伴うテストの回し方

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | vitest + happy-dom | 既存の vitest にそのまま乗る。Red/Green のループが速い | 実ブラウザとの差が残る |
| B | vitest + jsdom | 実装が枯れていて互換性が高い | 起動が遅い |
| C | Playwright で実ブラウザ | N-7 を直接検査できる | CI とループが重くなる |
| D | DOM に触れない層だけテストする | 依存が増えない | **描き直しの誤りをテストが捕まえられない**。再計算が UI に出るかは M3.5 の主題そのもの |

## 決定

**UI は React（案 B）、テストは vitest + happy-dom（案 A）、ビルドは Vite。**

### React を採る理由

**M3.5 の目的が「UX の前提を早期に検証する」ことだから。** M6 で React に載せ替えるなら、
M3.5 で確かめた形は確かめ直しになる。**検証は本番と同じ構成でやらなければ検証にならない。**

N-3（500KB gzip）に対して React は gzip 約 45KB で、1 割弱しか使わない。
**「素の DOM で始めて、足りなくなったら載せ替える」は、載せ替える時期が M6——
UI の分量が最大になる時点——になる**ので、安くならない。

### happy-dom を採る理由

**Red を出せることが条件**で、案 D はそれを満たさない。M3.5 が確かめるのは
**再計算の結果が画面に出ること**であり、DOM に触れない層だけをテストすると、
その主題がテストの外に落ちる。

jsdom（案 B）との差は速度だけで、**happy-dom で足りなくなったら差し替えられる**
（テストの側は `@vitest-environment` の指定を変えるだけ）。
Playwright（案 C）は N-7 を直接検査できるが、**N-7 を検査する必要が出るのは M6** であり、
今それを入れるとフィードバックのループが重くなる。**両立できるので、要るときに足す。**

### テストの環境は設定ファイルではなくファイル先頭で指定する

`vitest.config.ts` に環境の振り分けを書かず、DOM が要るテストの先頭に
`// @vitest-environment happy-dom` を置く。**どのテストがブラウザを前提にしているかが
そのファイルを開けば分かる**ためで、`core` のテストが Node の環境のまま走ることも保証される。

## 影響

- `packages/web` を追加する。依存は `react` / `react-dom` と `@sec/core`。
  開発時の依存に `vite` / `@vitejs/plugin-react` / `happy-dom` / `@testing-library/react`
- **ルート `package.json` の `typecheck` に `packages/web/tsconfig.json` を足す**（ADR-0001 の影響）
- `vitest.config.ts` の対象に `packages/*/src/**/*.test.tsx` を足す
- **依存方向は変わらない**（`core ← web`）。`packages/core/tsconfig.json` の
  `lib: ["ES2023"]`, `types: []` は緩めない。DOM を読み込むのは `packages/web/tsconfig.json` だけ
- **`core` は React を知らない。** UI は `LiveSheet` を呼ぶだけで、`core` 側に
  React 向けの入口（hook など）を作らない

## 覆すとしたら

- N-3（500KB gzip）に収まらなくなったとき → 軽量フレームワーク（案 C）へ載せ替える。
  React の API に寄せた Preact なら差し替えの費用が小さい
- happy-dom と実ブラウザの差でテストが嘘をつき始めたとき → jsdom へ、それでも駄目なら
  Playwright を足す（置き換えではなく、N-7 を見る層として足す）
