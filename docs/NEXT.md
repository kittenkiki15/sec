## 段階 4（#6）で確定させた判断（レビュー対象）

ADR が 1 本（[0018](adr/0018-golden-macro-directive.md)）。**要件定義書は変更していない。**

- **ゴールデンテストのケースに開始記号を持たせた**（ADR-0018）。最初の行の `!macro` で
  マクロとして読む。**`^ 3` は数式なら `#Syntax`、マクロなら `3`** で、指定する手段が
  無いままでは同じ原文に矛盾する期待値が 2 つ並ぶ。**宣言部を持つ定義は `!macro` に
  起動するメッセージを添える**（`!macro from: 1 to: 3`）
- **開始記号は 3 つ。** 数式が 1 つ、マクロが 2 つ（宣言付き / 本体だけ）。
  ブックに保存する経路（F-3-1）と、その場で試す経路（受け入れ基準 3、F-6）の両方が要る
- **セレクタの理解は文脈に依存しない。** 数式とマクロの違いは構文だけで、`do:` は
  数式からも送れる（何も観測できないだけ）。§6.4 が送ってきた宿題への答え
- **代入は式ではなく文。** Smalltalk-80 とは違う。数式が拒否する範囲が構文の 1 箇所で
  決まる。`3 + (a := 1)` も `a := b := 3` も `#Syntax`
- **ブロックの中の `^` は非局所リターン。** 繰り返しから抜ける手段をこれ 1 つにした
- **`do:` と `whileTrue:` を §7 に入れた。** §5.3・§6.4・付録 B が「§7 で決める」と
  していた宿題を閉じた。**カスケード `;` は入れない**（§1.6 のトークンからも外した）
- **範囲への代入は先送り**（§7.9）。未決論点 D-4（スピル）と絡むため、
  D-4 より先に単一値だけ決めると食い違う
- **実行上限は数式にも当たる**（§7.8）。要件 N-5 と F-3-5 はマクロについて書いているが、
  `whileTrue:` は数式からも送れる。**代入が書けないことは止まる保証にならない。**
  要件の変更ではなく適用範囲の明示として仕様書に書いた（AI レビュー 1 回目の指摘）

### 字句解析器で確定させた判断

仕様書の列挙に無かった 3 点を利用者に確認して決め、**§1.4 / §2.1 / §2.3 と付録 A に書いた。**
ADR は立てていない（新しい論点ではなく、既存の規則の適用範囲の明示）。

- **範囲トークンも「一次式の終端」に含める。** `A1:B2 -3` の `-` は二項セレクタ。
  §2.1 の列挙が `primary` のうち範囲だけ落としていた
- **`#` の後ろは綴りとして読む。** `#A1` はシンボル。§1.2 の「常にセル参照」は
  式の中で識別子と分ける規則で、シンボルの綴りには及ばない
- **空白の無い `a:=1` は代入。** キーワード `a:` と二項の `=` には切らない。
  §1.4 の最長一致に対する唯一の例外で、Smalltalk-80 と同じ

**トークンは原文のまま持たせ、値への変換はしない。** `007` → `7`、`1e3` → `1000` は
構文解析器が AST を組むときに行う。小数の変換は倍精度に収まらなければ `#Overflow`（§2.1）で、
エラーを作る役目を木の側へ寄せた方が、字句解析器が位置と種別だけを見る形で済む。

### 構文解析器（数式）で決めたこと

**構文解析器は開始記号を 3 つ持つ**（§7.1）。1 PR 400 行の目安に収めるため、
**数式（`formula`）とマクロ（`macro definition` / `macro body`）で 2 段階に分けた。**
段階 2 が数式の側で、`parseFormula` だけを持つ。

- **AST に範囲専用のノードを作らない。** `A1:B10` は `to:` の送信へ脱糖する（§4.3 のとおり）
- **セル参照は原文の綴りをそのまま持つ。** 列と行への分解はシートの側の仕事。
  `A007` と `A7` を同じセルと見るかも、そこで決まる（本書・仕様書とも未決）
- **倍精度に収まらない小数のリテラルは `ErrorNode`（`#Overflow`）として木に載せる**
  （§2.1、ADR-0013）。構文エラーではないので `ParseError` にしない。
  **構文解析の段階で生じるエラーの種別はこれだけ**
- **数式が拒む構文（代入・文区切り・返却・一時変数の宣言）は `parseFormula` が弾く。**
  §7.3 が「数式が拒む範囲を構文の 1 箇所で決める」とした形をそのまま実装にした
- **`LexicalError` と `ParseError` は別のクラスのまま。** どちらも利用者には `#Syntax` で、
  位置と説明文を持つ。**1 つにまとめるかは評価器が捕まえる形を書くとき（M2）に決める**
- **リテラル配列の裸のキーワードは、隣り合う間だけ 1 つのシンボルになる**（利用者の選択）。
  `#(at: put:)` は 2 要素。**Smalltalk の慣習に合わせた**（走査が文字を追う実装と同じ切れ方）。
  §2.4 と付録 A に書き、フィクスチャを 1 件足した。ADR は立てていない
  （新しい論点ではなく、既存の空白規則の適用範囲の明示）

### 構文解析器（マクロ）で決めたこと

**開始記号ごとに解析器を分けなかった。** 語彙も式もセレクタも 3 つで共通なので（§7.1）、
1 つの解析器が「文を受けるか」と「拒んだときに言う理由」だけを変える形にした。

- **ブロックのノードを一時変数と文の列を持つ形に一本化した。** 数式のブロックはその
  退化した場合（宣言なし・文 1 つ）になる。**評価器がブロックを 2 種類見ずに済む**
- **名前の静的検査を構文解析器に置いた。** 宣言の無い識別子への代入・引数への代入・
  二重の宣言・外側の名前を影にする宣言は、いずれも仕様が `#Syntax` と定めている
  （§7.3、§7.5）。評価まで持ち越す理由が無く、**位置を報告できるのもここだけ**
- **引数と一時変数は別の有効範囲に積む。** 同じ名前のとき「二重の宣言」ではなく
  「影」として理由を言えるようにするため
- **名前の影と二重宣言を数式のブロックにも当てた**（利用者の選択）。§7.5 の規則に
  §5.1 が触れていなかった。根拠が開始記号で変わらないため、§5.1 と付録 A に書き、
  `blocks.txt` にケースを 3 件足した。ADR は立てていない（既存の規則の適用範囲の明示）
- **代入の左辺は「左辺になれる綴りに `:=` が続く」ときだけ代入として読む。**
  `3 := 1` も `A1:B2 := 0` も式として読み切った後に `:=` が残り、そこで理由を言う

**フィクスチャとの突き合わせは構文の側だけ済ませた。** 全ケースを構文解析器に通し、
`#Syntax` を期待するケースだけが落ちることを確認してある（評価は M2）。

### セレクタ網羅の検査で決めたこと

**仕様書のセレクタ表にある綴りを送るケースが 1 件以上あることを検査する**（#21）。
CLAUDE.md の「組み込みセレクタを追加・変更したら対応するゴールデンテストも追加・更新する」を
機械的に確かめる検査にあたる。現時点の 59 セレクタはすべて満たしている。

- **拾うのは第 1 セルがちょうど `セレクタ` の表だけ。** 前方一致にすると §7.7 の
  「セレクタ（`do:` を含む）」や付録 A の「セレクタの文脈依存」が混ざる。綴りの一覧ではない
- **解析できないケースは `#Syntax` を期待していることを確かめてから飛ばす。**
  黙って飛ばすと、セレクタが数えられていないことと網羅の穴が見分けられない
- **抽出と収集を `tests/golden/selectors.mjs` に分けた。** 検査本体は仕様書と
  フィクスチャが揃っている限り緑のままなので、**抽出が壊れても素通りする。**
  単体テストを当てられる形にした
- **逆向き（フィクスチャにあって仕様書の表に無いセレクタ）は入れていない**（利用者の選択）。
  該当する 12 個のうち `foo` / `baz` / `rFF` / `max:min:` / `ifTrue:ifFalse:ifTrue:` は
  **わざと存在しないセレクタ**で、誤りと機械的に区別できない。`value:` / `value:value:` は
  §5.1 が本文で定めていて表から取れない。必要になったら §5.1 の表化と綴りの規約と併せて決める

**フィクスチャが緑になるのは M2（評価器）から。** M1 の完了条件は要件定義書 §8 のとおり
「仕様上の全構文をパースでき、構文エラーが位置付きで報告される」ことで、
ここまでは構文解析器の単体テストで確かめる。**満たしている**（`#19`）。

### 段階 1 で決めたこと

- **値は判別可能な直和**（`packages/core/src/eval/value.ts`）。整数は `bigint`、
  小数は `number`（ADR-0012）。**エラーも同じ直和の 1 つ**にした（要件 F-8-1）。
  **例外にしない。** 例外にすると評価の途中で制御が飛び、§6.0 の伝播順序
  （受け手 → 引数を左から右 → 送信）を値の受け渡しで表せなくなる
- **`Range` / `Interval` / `Cell` はまだ作っていない。** 送信かセル参照が要るため、
  2 回目に必要になるまで作らない
- **表記は `printValue` 1 つ**（§0.3）。**CLI と Web UI も同じ関数を使う。**
  指数表記の境界は ADR-0017
- **シンボルを引用符で囲むかは字句解析器に聞く**（`isBareSymbolSpelling`）。
  何が識別子・セレクタの綴りかは字句の知識であり、**表記の側で正規表現を写すと
  §1.2 / §1.4 を直したときに片方だけ古くなる**
- **`LexicalError` と `ParseError` は別のクラスのまま**（M1 からの持ち越しを閉じた）。
  評価器が両方を捕まえて `#Syntax` の値にする。利用者から見た区別は無いが、
  **字句の段階か構文の段階かは報告する側に要る**（要件 F-8-3）
- **まだ評価できないノードは例外**（`NotImplementedError`）。**仕様上のエラーではない。**
  黙って別の値を返すと、ゴールデンテストが「たまたま期待値と一致した」ことを検出できない

### 段階 2 で決めたこと

- **打ち切りを評価器の側に集めた。** エラーを受け取った時点で返すので、**送信まで届かない。**
  それを `ReceivedValue`（`Exclude<Value, ErrorValue>`）として型に出してあり、
  **打ち切りを忘れた経路は型検査で落ちる**
- **数の演算（`number.ts`）と振り分け（`send.ts`）を分けた。** 前者は §6.1 の「変換と範囲」
  だけを持ち、**引数の型の検査を持たない。** 数どうしの演算として閉じている方が、
  仕様書の表と突き合わせて確かめられる
- **整数と小数の比較は倍精度へ落とさない。** 落とすと桁が落ちて大小が逆転する
  （`9007199254740993 > 9007199254740992.0` が偽になる）。小数を整数部と端数に分けて
  任意精度の整数と突き合わせる。**比較は変換を伴わないので `#Overflow` にならない**（§6.1）
- **ブロックは木のまま値に載せる。** 条件式が選ばれた側だけを評価できるのは、引数が
  ブロックの**値**で渡り、呼ぶかどうかを送信の側が決めるからである（§5.2）
- **セレクタは対象のフィクスチャが送る分だけに絞った。** `Number` は
  `+ - * / abs negated squared > >= = max: min: between:and:`、`Boolean` は
  `ifTrue:ifFalse:`、`Block` は `value` だけ
- **持たせていないセレクタは `#DoesNotUnderstand` になる。** 未実装のノードを例外にしたのと
  違い、**これは仕様上ありうる値なので未実装の印にならない。** 取り違えを防ぐのは
  `COVERED` を段階ごとに増やす運用の側で、緑にしたファイルの中に未実装のセレクタが
  残っていれば期待値と食い違って落ちる

### 段階 3 で決めたこと

**新しい論点は出ていない。** §6.1 が既に定めていた規則をそのまま実装した。

- **`/` `//` `\\` は同じ商を経由する**（`decimalDivision`）。仕様が
  `self = (self // n) * n + (self \\ n)` を保つとしている以上、**剰余も商から求めるほかない。**
  `\\` が `//` と同じ条件で `#Overflow` になるのはその帰結で、別の規則ではない
- **`//` は整数を返すが範囲の制限を免れない。** 整数どうしなら整数演算のままなので
  上限が無く、小数が混ざれば商を小数で求めてから床を取るので、そこで超える
- **`sqrt` は受け手の変換が演算より先。** `1e400 sqrt` は結果の `1e200` が表せても `#Overflow`
- **`rounded` は `Math.round` と同じ規則**（端数ちょうど半分は大きい側へ）。
  `-2.5 rounded` が `-2` になるのは Smalltalk-80 と一致する

**段階 2 の「持たせていないセレクタは `#DoesNotUnderstand` になる」が実地で検証された。**
`numbers.txt` を対象に足した時点の失敗 38 件は**すべて未実装のセレクタ**で、
期待値と食い違って落ちた。**未実装が緑として紛れ込んだケースは無い。**

### 段階 4 で決めたこと

**仕様書が書いていなかった 2 点を利用者に確認して決めた。** どちらも ADR は立てていない
（新しい論点ではなく、既存の規則の適用範囲と、未決を残したままの暫定の実装）。

- **`'1.0e400' asNumber` は `#Overflow`。** §2.1 の形には合うが倍精度に収まらない。
  仕様が「新しい規則を作らず §2.1 を再利用する」としている以上、**再利用するのは形だけでなく
  値の作り方も含む**（ADR-0013）。§6.0 は「表のエラー欄が空」を**引数の型では失敗しない**
  意味と定めており、引数を取らない `asNumber` には当たらない。§6.2 と付録 A に書いた
- **非 ASCII は暫定。** 付録 B の未決 2 点（数え方・写し方）は**開けたまま**、実装は
  **コードポイントで数え**（字句解析器が列を数えるのと揃える）、**写像は実行環境の既定**に
  した。付録 B にその旨を書き足してある。**決めるのは UI を見てから**（M5）

**実装で決めたこと。**

- **`asNumber` は字句解析器に読ませる。** 数値リテラルの形を判定する規則を書き写すと、
  §2.1 を直したときに片方だけ古くなる。**綴りをトークンと突き合わせる**のは、前後の空白や
  コメントがトークンにならず、`' 42'` が `42` として読めてしまうため
- **等価性を受け手のクラスごとに書かず 1 箇所（`sendToAny`）に集めた。** `=` と `~=` は
  §6.1〜6.3 のどのクラスも同じ形で持ち、**足し忘れた 1 つが `#DoesNotUnderstand` になる。**
  `isNil` / `notNil` / `ifNil:` も受け手を選ばないので同じ場所に置いた。
  **要素で比べる `Array` / `Interval` はここに含めない**（§6.3、段階 6 で足す）
- **ブロックを引数に取るセレクタの型検査を `withBlock` に寄せた。** 短絡して引数を見ない
  経路（`false and: 1`）でも型は検査する。検査を条件分岐の中に書くと、**選ばれない側の
  検査が落ちても気付けない**（`booleans.txt` がこの 2 件を明示的に持っている）
- **`and:` / `or:` は選んだ側のブロックの値をそのまま返す**（Smalltalk-80 と同じ）。
  §6.2 の表は返り値を真偽値としているが、これは真偽値を返すブロックを渡す使い方を
  書いたもので、`true and: [1]` のような形は定めていない。**必要になったら決める**

### 段階 5 で決めたこと

**仕様書が書いていなかった 2 点を利用者に確認して決めた。** どちらも「§5.1 の規則が
どこまで及ぶか」の話で、ADR は立てていない（新しい論点ではなく、既存の規則の適用範囲の明示）。
**§5.2 と付録 A に書き、`conditionals.txt` にケースを 4 件足した**（32 → 36 件）。

- **引数の数の検査は、ブロックを評価する経路すべてに当たる。** `true ifTrue: [:x | x]` は
  `#TypeError`。§5.1 は「引数の数が合わなければ `#TypeError`」を `value` 系の送信について
  書いているが、**`value:` の送信に限った規則にすると、同じブロックが送り方によって
  別の意味を持つ**
- **ただし選ばれなかった側は検査もされない。** `false ifTrue: [:x | x]` は `nil`。
  **引数の型（ブロックかどうか）は引数そのものの性質で、評価せずに見えるので常に検査する**
  （`false and: 1` は `#TypeError`）。**引数の数が合うかは、ブロックを評価するときに
  初めて問題になる**

**実装で決めたこと。**

- **環境は平らな表 1 つにした**（`Environment = ReadonlyMap<string, ReceivedValue>`）。
  外側と同じ名前を内側で宣言できない（§5.1、§7.5）ので**名前が衝突せず、内と外を分けて
  持ってどちらを先に見るかを決める必要が無い。** 影を許す言語なら鎖が要るが、
  この言語は構文解析器が影を弾いている
- **ブロックは作られた時点の環境を捕まえる。** `[:x | [x + 1]] value: 2` の内側のブロックは、
  外側の送信が終わった後に評価されても `x` を見られなければならない
- **引数の数の検査を `invokeBlock` に置いた。** 条件式もブロックを引数なしで評価するので、
  **送信の側それぞれに書くと足し忘れた 1 つが検査を抜ける**（段階 4 で `withBlock` に
  型の検査を寄せたのと同じ理由）
- **束縛されていない識別子は `NotImplementedError` のままにした。** §4.2 は `#Ref` と
  定めているが、**それを返すのはセル参照が解決できるようになってから**でよい
  （`references.txt` は M3 待ちで、段階 5 のフィクスチャには 1 件も現れない）。
  先回りして足すと、段階 5 のどのケースも要求していない振る舞いが検査の外に増える
- **`Array` の `ifEmpty:` は段階 6 を待たずに入れた。** §6.3 ではなく**条件式として
  §5.2 の表にある**ためで、`conditionals.txt` が緑になる条件に入っている。
  §6.3 の残りのセレクタは段階 6

### 段階 6 で決めたこと

**仕様書が書いていなかった 2 点を利用者に確認して決めた。** ADR は立てていない
（新しい論点ではなく、既存の規則の適用範囲の明示）。**§6.3 と付録 A に書き、
`collections.txt` にケースを 31 件足した**（155 → 186 件）。

- **列挙のブロックが真偽値以外を返せば `#TypeError`。** §7.6 が `whileTrue:` について
  「受け手が真偽値以外を返せば `#TypeError`」と既に定めており、同じ規則を
  `select:` / `reject:` / `detect:ifNone:` / `sorted:` に当てた。**この言語は `false` 以外を
  真とみなす経路をどこにも持たない**（`false and: 1` も `#TypeError`）
- **`sorted:` は安定とする。** 決定性が要件（F-4-4）である以上、同順の要素の並びも
  定まっていなければならない。**実行環境の `sort` に任せると**、比較が不整合な
  ブロック（`[:a :b | true]`）を渡されたときの結果が**整列法ごとに変わる**

**配列の集計が値 `nil` の要素を無視するケースも足した。** ADR-0010 と §6.3 の表は
クラスを限らずそう定めているが、フィクスチャは範囲の空セルでしか確かめていなかった。

**実装で決めたこと。**

- **`Array` と `Interval` の演算を 1 箇所にまとめた**（`sequence.ts`）。2 つ目なので
  まとめた（CLAUDE.md の「2 回目に必要になるまで抽象化しない」）。**`Range` が 3 つ目として
  M3 で乗る。** そのときは要素が `Cell` になり、**集計の前に値へ解決する段が要る**
- **要素を並べるのは集計と列挙だけにした。** `size` / `isEmpty` / `at:` / `first` / `last` は
  個数と位置だけで決まるので、**`1 to: 1e400` のような区間にも答えられる。**
  区間どうしの `=` も要素を並べない（下端と個数が一致することは、要素がすべて等しいことと
  同じである）。**個数が極端に大きい区間を列挙したときの打ち切りは要件 N-5**（#27）
- **`sorted:` は自前の併合整列。** 実行環境の `sort` は比較が不整合な述語に対して
  結果がエンジン依存になる。**併合整列なら比較の順序と結果がどの述語に対しても定まる**
- **ステップ数の上限を入れた**（`budget.ts`、AI レビューの指摘を受けた利用者の選択）。
  **この段階が「止まらない数式」を初めて到達可能にした**（`whileTrue:` は M4 で未実装、
  深い再帰は `RangeError` の安全網が拾える）。CLAUDE.md の規約 4 は評価器のループに
  上限を課しており、それを破るループを足したことになる。
  **数えるのはステップ数だけ。** 時間はマシンの速度で結果が変わり、決定性（F-4-4）を
  満たさず `#Timeout` のケースをゴールデンテストに書けない
- **列挙は要素の数だけ先に払う。** `1 to: 1e400` は 1 歩も進まず、**配列を確保する前に**
  `#Timeout` になる（個数を先に決めてあることがここで効く）。
  指摘の前は OOM でプロセスが落ちており、**`RangeError` の安全網では拾えなかった**
- **「ブロックを評価しなければ引数の数も返り値も問われない」は、受け手が空の場合に
  限らない**（§5.2 の規則そのまま）。`sorted:` の比較は要素が 2 つ以上なければ起こらず、
  **要素が 1 つなら評価もされない**（`#(1) sorted: [:a :b | a / 0]` は `#(1)`）。
  仕様書に空の受け手の例しか書いていなかったので、`sorted:` の例を足した
- **予算切れは値ではなく打ち切りとして扱う。** リテラル配列の要素を評価している途中で
  尽きたとき、`#Timeout` を要素に混ぜると**打ち切られたことが式の値から読み取れない**
  （`#(1 1 …100 万…) first` が `1` を返していた）。**要素の `#Overflow` とは分ける**
  ——あちらは表せない値であって、評価が途中で止まったわけではない
- **等価性は 1 箇所（`isEqual`）のまま、要素どうしの比較を受け取る形にした。**
  そのため受け手だけでなく**要素**も比べることになり、ブロックとエラーが現れうる。
  どちらも `=` を持たないが **`=` はエラーにならない**（§6.3 の表）ので、
  ブロックは等しくないとみなし、エラーは種別で比べる（下の「積んであるもの」）

### 段階 7 で決めたこと

**持ち越していた論点を 1 つ閉じた**（下の「積んであるもの」から外した）。ADR は立てていない
（新しい論点ではなく、既存の規則の適用範囲の明示）。**§3.8 と付録 A に書いた。**

- **構文エラーの位置と説明文は値に載せず、値と組にして返す。** `evaluateFormula` の戻り値を
  `{ value, diagnostic? }` に変えた。`ErrorValue` に載せると「**同じ `#Syntax` でも位置が
  違えば別の値か**」を決めることになるが、§6.0 は「エラーはメッセージを受け取らない」と
  しか定めていない。組にすれば値の側は今のままで済み、M5 の Web UI も同じ形を使える
- **診断が付くのは構文エラーだけ。** 実行時のエラー（`#DivideByZero` など）は位置を持たない。
  **評価器は原文のどこを見ているかを追っていない**ためで、追わせるより持てない段階を
  型で言う方が安い。`phase` で字句と構文を分けてあるのは、利用者には同じ `#Syntax` でも
  報告する側には要るため（要件 F-8-3、段階 1 からの持ち越し）

**CLI で決めたこと。**

- **範囲は `sec eval` だけ。** 要件定義書 §8 の M2 完了条件がそれだけを求めている。
  `parse` / `run` / `bench`（開発方針）と REPL（受け入れ基準 1）は必要になった段階で足す
- **stdout は値の表記だけ、診断と使い方は stderr。** 混ぜると `pnpm sec eval ...` の出力を
  そのまま値として受け取れない。**表記は `printValue` 1 つ**で、CLI 専用の字面を作らない
  （作るとゴールデンテストの期待値と CLI の出力が食い違う）
- **終了コードは 0（値）/ 1（エラー値）/ 2（使い方の誤り・未実装）。** エラーは値だが
  （要件 F-8-1）、`&&` でつないだときに失敗が伝わる方が、**出力の字面を読まずに正誤を
  判定できる**（開発方針「フィードバックループは CLI で回す」）
- **まだ評価できない式は 2 で、エラー値にしない。** `A1 + 1` を `#Ref` に化けさせると、
  実装済みかどうかが出力から読み取れなくなる（評価器が `NotImplementedError` を
  例外にしているのと同じ理由）
- **判断を持つ `runCommand` と process に触れる `main.ts` を分けた。** 出力先と終了コードを
  値として返せば起動せずに確かめられる。**起動して初めて分かることだけを `main.test.ts` が
  見る**（出力先の取り違えと終了コードの落とし忘れは、純粋な関数のテストでは捕まらない）
- **式は 1 つだけ受ける。** 黙って 1 つ目を評価すると、シェルの引用符を書き損ねて式が
  分かれたときに、別の式の結果を正しい答えとして受け取ってしまう
- **ビルド段を置かず `node` が `.ts` を直接読む。** `engines` を `>=22.18` に上げたのは、
  型の除去が既定で有効になるのがその版からであるため

### 順序の理由

**評価器を先に閉じ、再計算エンジンを後に置く。**

- **段階 1〜4 のシートは定数セルだけを持つ。** 数式セル（`!B1 := =A1 + 1`）の値を出すには
  数式を評価する必要があり、その数式はセル参照を含む。**セル参照が評価できるようになる前に
  再計算エンジンは書けない**（段階 2 が段階 5 に先行する理由）。
- **依存の抽出は範囲を知っていなければならない。** `A1..A3 sum` は 3 つのセルに依存する。
  **範囲が値として存在しない段階でグラフを組むと、後で抽出を書き足すことになる**
  （段階 4 が段階 5 に先行する理由）。
- **フル再計算と増分再計算を分ける。** 同じ依存グラフを使うが、
  1 PR 400 行の目安に収めるために段階 5 と段階 6 に割る。

**ファイルを `COVERED` に足す時期は、そのファイルに緑のケースが 1 件でもできた時点。**
保留のケースは飛ばされるので、全件が緑になるまで待つ必要はない。`references.txt` は
現時点で 28 件すべてが保留のため、**段階 2 まで対象に入れられない**（ハーネスが
「全件保留のファイル」を落とすようにしてある）。

### 段階 0 で決めたこと

- **番地は「列の綴り + 行の数値」に正規化する**（[ADR-0020](adr/0020-cell-address-normalization.md)）。
  **`A007` は `A7` と同じセル。** 行は §4.1 が桁数を制限していないので `bigint` で持つ。
  列は双射基数 26（`Z` の次が `AA`）で前ゼロにあたる綴りが無く、正規化する余地がない。
  **`A0` が `#Ref` なのは変わらない**（正規化した結果が 0 なら解決できない、と読む）
- **数式でないセルの内容はリテラルとして読み、読めなければ文字列にする**
  （[ADR-0021](adr/0021-cell-content-interpretation.md)）。`=` で始まれば数式 →
  §2 のリテラルちょうど 1 つとして読めればその値 → それ以外は内容そのままの文字列。
  **`1.0e400` は `#Overflow` であって文字列ではない**（リテラルとして読めるかは構文で決まり、
  値がエラーかどうかは関わらない）。**空の内容は空セルで値は `nil`**（ADR-0010）
- **`ranges.txt` と `assignment.txt` を `COVERED` に足した。** どちらも
  「範囲にならない書き方」「数式に代入は書けない」を**今の評価器だけで判定できる。**
  17 件が回帰検査に入った

### 段階 1 で決めたこと

**仕様書が書いていなかった 2 点を利用者に確認して決めた。** ADR は立てていない
（新しい論点ではなく、ADR-0021 が決めた 3 段の適用範囲の明示）。**§4.4 と付録 A に書いた。**
どちらも**原文の見た目どおりに読む**側へ寄せている。

- **先頭に空白のある `  =A1 + 1` は数式にしない。** 段 1 は原文の 1 文字目だけを見る。
  前後の空白を無視してから `=` を探すと、**打ち間違えて入った空白が黙って数式を殺す。**
  Excel も同じで、表計算の慣習とも揃う
- **空白だけの内容は文字列。** 空セルは原文が空文字列のときだけである。段 2 が前後の空白を
  無視するのは §1.1 の字句の規則であって、**内容が空かどうかの判定ではない**

**実装で決めたこと。**

- **番地を読むのと解決できるかは分けた**（`parseAddress` と `isResolvable`）。
  `A0` は形としては番地なので `parseAddress` は通す。**弾いてしまうと「形が違う」と
  「指す先が無い」を呼び出し側が区別できず**、§4.2 が `#Ref` と定めた方を報告できない
- **`isResolvable` は列の綴りも検査する**（AI レビューの指摘）。番地は構造型なので、
  `parseAddress` を通さない `{ column: 'A1', row: 2n }` を呼び出し側が組み立てられ、
  **`printAddress` の連結がシートのキーを `A12` にして別のセルと衝突していた。**
  シートは**読み書きの両方で、キーを組み立てる前に**検査する。
  **型を不透明にして `parseAddress` 経由でしか作れなくする案は採らなかった**——
  消費者が `core` の中だけの今は検査 1 箇所で足り、**列と行を組み立てる入口は
  `Range` の列挙（段階 3）で要る**ので、そのとき生成の側と併せて決める方が安い
- **内容がリテラルかどうかは構文解析器に読ませる。** 判定の規則を書き写すと §2 を直したときに
  片方だけ古くなる（`asNumber` を字句解析器に読ませたのと同じ理由、M2 段階 4）。
  そのために**リテラルの評価を `evaluateLiteral` として外に出した。**
  原文を `evaluateFormula` に渡し直す形でも書けるが、呼び出し側が既に木を持っているのに
  同じ原文を 2 度解析することになる
- **シートは原文だけを持ち、値を持たない。** 数式セルの値は他のセルの値に依存する（§4.2）ので、
  値まで抱えると**内容の解釈が再計算を知ることになる。** 原文を本体にしておく向きは、
  保存・読み込み（F-5-1）と数式バー（F-7）が要求する形でもある
- **空の内容を置くことはセルを空にすること**（ADR-0010）。持ち続けると「内容が空文字列のセル」と
  「空のセル」が表の上で別物になるが、**その 2 つを区別する規則はどこにも無い**
- **解決できない番地への書き込みは例外。** 作れてしまうと `A0` が値を持ち、§4.2 が破れる。
  **`RangeError` は使わない**——評価器が深い入れ子の安全網としてそれを捕まえており
  （`evaluateFormula`）、セルへの代入（§7.4、M4）が評価の途中でここを呼ぶようになったとき、
  **呼び出し側の誤りが `#Timeout` に化ける**

### 段階 2 で決めたこと

**仕様は §4.2 が既に書き切っていたので、決めたのは実装の形だけである。**
ADR も仕様書の変更も無い。

- **`Cell` に保持する値を持たせず、引く手段（番地 → 値の関数）だけを持たせた。**
  §4.3 が「範囲は座標の対でしかなく、作るだけならセルに値が入っている必要はない」と
  定めており、**値を抱えると範囲を作るだけで両端を読むことになる。**
  数式セルの値は他のセルに依存する（段階 5）ので、読む回数は少ない方がよい。
  **段階 4 の列挙も同じ手段を要る**（要素が `Cell` になる）
- **その関数（`CellValues`）をシートそのものにしなかった。** 数式セルの値は再計算の結果で
  あって内容ではない。**段階 5 では再計算エンジンが同じ形の関数を差し出し、評価器は変わらない。**
  `packages/core/src/model/values.ts` が今の実装で、**定数セルだけを値にする**
  （数式セルは `NotImplementedError`）
- **`Cell` 自身が理解するセレクタを評価器（`evaluate.ts`）に置いた。** §4.2 の規則 1 と
  規則 2 の分かれ目そのものなので、`send.ts` に分けると**片方だけ足したときに
  委譲の向きが狂う**
- **`Cell>>to:` は `#DoesNotUnderstand` にせず例外にした**（段階 3 で実装する）。
  仕様が定めた送信（§4.3）を「理解しない」と偽ることになるうえ、委譲へ回すと
  `A1 to: A3` が**値の区間**（`1 to: 3`）になる。**`collections.txt` の保留のケースが
  いくつか、範囲でないものでたまたま緑になってしまう**
- **シートを渡さない評価はどのセルも空として扱う。** `sec eval 'A1'` は `nil`。
  空のシートを渡したのと同じで、空セルの値は `nil`（ADR-0010）。**仕様の話ではなく
  API の既定値**なので、仕様書には書いていない
- **`isEqual` は両側のセルを解決してから比べる**（§4.2 の「`Cell` は `=` を定義しない」）。
  受け手としてセルがここへ来ることはない（送信の直前に解決される）が、
  **段階 4 の列挙は配列の要素としてセルを渡す**

### 段階 1 から持ち越した宿題のうち、ここで埋めたもの

- **セルの内容の解釈（§4.4）と番地の正規化（ADR-0020）にフィクスチャが当たるようになった。**
  `references.txt` に 12 件足した。**ただし空白の絡む 3 件は単体テストのまま**——
  ゴールデンのセルの指定（`!A1 := 内容`、ADR-0009）は**内容の前後を落とす**ので、
  `  =1 + 1` が数式にならないことも、空白だけの内容が文字列になることも書けない。
  **区切りの規則に手を入れれば書けるが、それは ADR-0009 の変更になる**ので見送った
- **評価器が例外にしていた 2 つのうち、束縛されていない識別子を閉じた**（`#Ref`）。
  `cell` ノードも閉じ、**残る例外はセルからの範囲（段階 3）とマクロ（M4）だけ**

### 段階 3 で決めたこと

**仕様は §4.3 と §6.3 が既に書き切っていたので、決めたのは実装の形だけである。**
ADR も仕様書の変更も無い。

- **範囲に値を引く手段を持たせなかった。** `Cell` は持っているが（段階 2）、範囲は
  **座標の対でしかなく**（§4.3）、`=` も正規化した矩形だけで決まる（§6.3）。
  **中身を読むのは列挙と集計だけ**なので、持たせるのは段階 4 でよい
- **向きの正規化は値を作る時点で済ませる**（`eval/range.ts`）。読む側が向きを気にしなくてよく、
  **`=` が端どうしの比較で済む。** 列挙（段階 4）も左上から右下へ進めばよくなる
- **列の大小を `model/address.ts` に置いた**（`compareColumns`）。列が双射基数 26 で
  **辞書順ではない**のは番地の綴りの性質であって、範囲の都合ではない。
  段階 1 が「列と行を組み立てる入口は段階 3 で要る」と書いていたのがここで、
  **組み立てる成分がどちらも解決できる番地から来る**ので、検査を足す必要はなかった
- **引数がセルでない `to:` は `#TypeError`。** 受け手がセルである以上 `to:` は理解しており、
  合わないのは引数の型である（§6.0 の検査の順序）。§6.3 の `Cell` の表のとおり
- **`Range` は `send.ts` の振り分けで「何も理解しない」ままにした**（段階 4 まで）。
  `#DoesNotUnderstand` は仕様上ありうる値でもあり（`A1:B2 -3`）、
  **未実装であることの印にはならない。** 取り違えを防ぐのは `!pending` の側（ADR-0019）

### 段階 3 で印が外れた想定外の 3 件

**ハーネスが「通ってしまった保留」として知らせた**（ADR-0019）。段階 4 の分と見ていたものが、
段階 3 で緑になった。

- **`=` と `~=` は受け手のクラスを選ばない経路にある**（`sendToAny`）。範囲の `=` を
  足した時点で `collections.txt` の 2 件が緑になる。§6.3 の表に載っているが、
  **段階 4 を待つ理由が無い**
- **`A1..A3 collect: [:c | c * 2]` は別の理由で緑になっている。** 期待値は
  `#DoesNotUnderstand` で、意図は「空セルの `nil` に `*` を送れない」ことだが、
  いまは `collect:` そのものを範囲が理解しない。**段階 4 で意図どおりの理由に変わり、
  期待値は変わらない**ので印は戻さない

### 段階 4 で決めたこと

**仕様は §6.3 が既に書き切っていたので、決めたのは実装の形だけである。**
ADR も仕様書の変更も無い。

- **範囲に値を引く手段を持たせた**（`CellValues`）。段階 3 が「中身を読むのは列挙と
  集計だけなので、持たせるのは段階 4 でよい」としていたのがここ。**矩形の全セルを
  抱える形は採らない**——それでは範囲を作るだけで中身を読むことになり、§4.3 が
  「作るだけならセルに値が入っている必要はない」と定めた理由が消える。
  **列挙が渡す要素は `Cell`**（ADR-0015）なので、要素にそのまま渡す手段でもある
- **集計だけが値へ解決する段を通る**（§6.3）。`Cell` そのものは `nil` ではないので、
  この段が無いと**空セルを数えてしまう。** 列挙が同じ段を通らないのは、解決して渡すと
  **ブロックの中でセル自身を扱えなくなる**ため（`A1..A3 collect: [:c | c value]`）
- **解決はクラスを選ばない。** `Range` の要素だけでなく、`select:` が返した配列の要素も
  `Cell` のままである。**§6.3 は「集計は要素を値に解決してから扱う」と書いており、**
  受け手のクラスで分けていない
- **`ifEmpty:` は範囲を受け手にしない**（§6.3 の「空になりうるのは `String` /
  `Array` / `Interval`」）。理解させて受け手をそのまま返しても値は同じだが、
  **空になりうる型の一覧が仕様と食い違う。** 常に偽になる条件を書けることは、
  書き手にとって誤りの合図である
- **列の綴りの位置（双射基数 26）は `model/address.ts` に置いた。** `Z` の次が `AA` に
  なるのは番地の綴りの性質であって範囲の都合ではない（`compareColumns` と同じ理由）。
  **綴りのままでは隣の列を求められない**ので、列挙は位置に直してから 1 ずつ進める
- **行優先の並びは `range.ts` が持つ**（`rangeCellAt`）。位置から番地を計算するので、
  **`at:` / `first` / `last` は矩形を並べずに答えられる**（区間の要素と同じ扱い）

### 範囲の大きさに上限が無いことを確かめた

段階 3 が宿題に残していた点。**`A1..A99999999999999999999` は書けて、`size` は
`bigint` で答えられる**（座標の引き算で決まる）。**列挙は要素の数だけ先にステップを
払う**ので（`elementList`）、並べる前に `#Timeout` になる。区間と同じ経路で、
`(1 to: 1e400) collect:` が `#Timeout` になるのと同じである。ゴールデンテストに
4 件足した（`size` / `collect:` / `sum` / `last`）。

### この段階で残した論点は閉じた（#51）

**ブロックが `Cell` を返したとき条件として読めるか**は、段階 4 の時点で仕様書が触れて
おらず、実装だけが `#TypeError` と答えていた。**利用者の判断で `#TypeError` に確定した**
（委譲は送信に対する規則であって、ブロックの値を条件として読むのは送信ではない）。

**そのぶん、セルを条件にする明示的な手段として `isTrue` を足した**（ADR-0022）。

- **`isTrue` はすべての値が理解する**（`isNil` / `notNil` と同じ列）。受け手が `true` の
  ときだけ `true`。**`Cell` 自身のセレクタにはしない**——§4.2 の規則 1 の一覧が増えると
  委譲の境界が広がり、**列挙の結果（`Array`）には使えなくなる**（§6.3 の「列挙の結果は
  常に `Array`」がそれを要求する）
- **能力そのものは元からあった。** `A1..A3 select: [:c | c = true]` は `isTrue` の前から
  動く（`=` は受け手のクラスを選ばず、セルは委譲で解決される）。**足したのは読みやすい綴り**
- **真偽値でない値を `false` に畳むが、条件として読む側の規則は変えていない。**
  `1 ifTrue:` も `#(1 2) select: [:x | x]` も従来どおりで、フィクスチャに固定してある
- **`isFalse` は入れない。** `c isTrue not` で足りる（2 回目に必要になるまで抽象化しない）
- **`whileTrue:`（§7.6、M4）がこの決定の再考の機会になる。** どちらに転んでも `isTrue` は
  短縮形として残るので、決定とは両立する

### `sec eval` から到達できる未実装が無くなった

**CLI の終了コード 2（未実装）を検査するケースが 1 件減った**（`packages/cli/src/command.test.ts`）。
`sec eval` は数式しか受けず、**そこから届く未実装が範囲で尽きた**ためである。
残る未実装は数式セル（シートが要る、段階 5）とマクロ（`sec` がまだ読まない、M4）で、
どちらも引数の式からは届かない。

**経路そのものは残した。** 消すと、次に未実装へ当たったときに例外がそのまま漏れて、
**終了コード 1（エラー値）と見分けが付かなくなる。**

### 段階 5 で決めたこと

**方式は利用者が選んだ**（[ADR-0023](adr/0023-dependency-extraction.md)）。
静的な抽出と遅延の安全網を両方持ち、**抽出は差し替えられるようにしてある。**

- **静的な依存グラフが順序を決め、遅延と進行中の印が正しさを持つ。** 抽出が何を返しても
  値は変わらず、変わるのは評価の順序と再帰の深さだけである。**依存を 1 つも返さない
  抽出でも値は正しく出る**ことを単体テストで固定した（`recalc.test.ts`）
- **順序が要るのは深さのためである。** 安全網だけでも値は出るが、参照の鎖の長さが
  そのまま再帰の深さになる。**1000 段の鎖**を評価するテストがその検査にあたる
- **トポロジカル順序に載らなかったセルを、そのまま `#Circular` にはしない。**
  載らない理由は「本当に巡っている」と「多めに取った依存で巡って見える」の 2 つで、
  **後者は循環ではない**（`=A1..A3 size` は `A1` を読まないが矩形には入る）。
  評価してみれば区別が付く
- **矩形は数式セルとの交わりだけを見る。** 矩形の中の番地を数え上げると
  `A1..A1000000` で番地の数だけ費用がかかる。**シートは疎**なので、持っているセルの側から
  矩形に入るかを見る方が安い
- **抽出の差し替えは `RecalculationOptions.dependencies`**（利用者の要望）。段階 7 の
  `sec bench` が性能要件を測ったとき、**抽出の粗さが解決策になりうる**

### 受け手のセルを解決する時期を仕様書に書いた

**ゴールデンテストが論点を突いた。** `errors.txt` が M0 から
「`!A1 := =A1` のとき `A1 + (1 / 0)` は `#Circular`」と固定していたが、
引数を先に評価すると `#DivideByZero` になる。

**受け手の解決を引数の評価より前に出した**（利用者の選択）。§6.0 の「受け手が先」を
**順序として読む**——受け手の値がエラーなら引数に到達しない。`A0 + (1 / 0)` が `#Ref` に
なるのと同じである。§4.2 と付録 A に書いた。

**規則 1（`value` / `to:`）では解決しない**ので、§4.3 の「範囲はセルの値を読まない」は
そのままである。`A1..A3 size` は循環しているセルからでも `3` で、`count` は `#Circular`。
**この違いをフィクスチャに固定した**（`ranges.txt` の 2 件）。

**「循環は参照そのもののエラー」（`#Ref` と同列）という読み方は採らなかった。**
そうするとセル参照を評価した時点で値が要り、**範囲を作るだけで両端を読む**ことになる。

### 構文解析と評価を分けて呼べるようにした

`parseFormulaOrFail` と `evaluateParsedFormula`（`eval/evaluate.ts`）。
**再計算は同じ木を依存の抽出と評価の両方で使う**ので、原文から評価し直すと
シートの全数式を 2 度解析することになる。`evaluateFormula` はこの 2 つの合成になった。

**既存のテストが振る舞いを担保する機械的なリファクタリング**なので、
テストを先に書いていない（CLAUDE.md の例外）。

### 段階 6 で決めたこと

**2 点を利用者と決めた**（[ADR-0024](adr/0024-incremental-invalidation.md)）。
**開発方針が「依存グラフと増分再計算の設計は一緒に」としている箇所である。**

- **無効化は「実際に読んだ番地の記録」で決める。** ADR-0023 は静的な抽出の逆向きを
  使う見込みだったが、**抽出は範囲の端が式のとき取りこぼす。** フル再計算では
  順序が粗くなるだけで安全網が正したのに対し、**増分では取りこぼしがそのまま
  「古い値が残る」形で表に出る**（安全網が動く機会を与えられない）
- **`Sheet` を包む `LiveSheet` が書き込みと無効化を兼ねる。** 別々に呼べる形にすると、
  **伝え忘れた値が黙って古いまま残る。** `Sheet` を内部に持ち、外から書けなくした。
  `put` は**計算し直したセルの番地を返す**（グリッドの描き直しに要る、要件 F-7）
- **ADR-0023 の分担は動いていない。** 静的な抽出は今までどおり順序だけを決める。
  変わったのは、**無効化という別の役割に別の材料を当てた**ことである。
  「依存を 1 つも抽出しない実装でも値は正しい」はそのまま成り立つ
- **短絡して読まなかったセルは依存ではない。** ADR-0023 が案 B の欠点として挙げていた点だが、
  **読まなかったセルはその数式の値を変えない。** 枝が切り替わるときは条件にしたセルが
  先に汚れるので、そこで新しい値を読む。**数式が副作用を持たず**（F-2-10）**評価が
  決定的である**（F-4-4）ことから帰納的に言える
- **空セルを読んだことも覚える。** 記録するのは読んだ番地であって、内容のあるセルではない。
  覚えていないと、**後から内容が入ったときに下流と見なせない**（ADR-0010）
- **索引は差し替えられる**（`LiveSheetOptions.invalidation`、利用者の要望）。
  観測には**読みと静的な依存の両方**を渡すので、静的な逆向きを引く索引も後から書ける

### 段階 7 で決めたこと

**3 点を利用者に確認して決め、[ADR-0025](adr/0025-performance-benchmark.md) に書いた。**

- **絶対しきい値で合否を出す**（要件の数字をそのまま判定基準にする）。超えたら終了コード 1。
  **「CI で回帰を検出する」はログの数字を人間が読む形では成り立たない。**
  基準値ファイルとの相対比較は採らなかった——**更新すれば緑になる**ので歯止めにならない
- **合否を持つので ADR-0004 の「性能ベンチマーク」例外は当たらない。** 例外は
  合否判定が無いものに限る。**テストを先に書いた。** 断言しないのは計測値そのものだけで、
  **シナリオの形・中央値の採り方・しきい値の当て方**は振る舞いとして固定してある。
  **時計を差し替えられる**ので、中央値を採ることは実時間に依存せず検査できる
- **測る形は 2 本**（スカラ鎖・範囲集計）。段階 6 の手元の計測が範囲を含んでいなかった
- **しきい値は 10,000 セルのときだけ当てる。** 要件が数字を定めているのはその規模だけで、
  別の規模に当てると根拠の無い合否になる。**比例させて当てる案は採らなかった**——
  再計算が規模に対して線形である保証はどこにも無く、要件が言っていないことを言うことになる
- **中央値を採る**（平均ではない）。1 回の跳ねが報告値を動かさない。**偶数回なら小さい側**
  ——2 つの平均は、実際には 1 度も測っていない値になる。**1 回目は捨てる**（暖機）
- **シナリオを値として取り出せる**（`Scenario`）。番地や数式を組み立て損ねた形は `#Ref` を
  並べるだけのシートになり、**速いが何も測っていない。** 形が狙いどおりかを計測なしで
  検査できるようにした
- **AI レビューが停止しない入力を見つけた**（[#59](https://github.com/kittenkiki15/sec/pull/59)）。
  倍精度に収まらない綴り（`9` が 400 個）は `Number` が `Infinity` にするが、
  **`Infinity <= 0` は false なので下限の検査を通る。** シナリオの構築は 1 ずつ
  数え上げるため、`sec bench <巨大な数字>` が終端に到達せず停止しなかった。
  **「そんな入力は来ない」で省いた検査が、止まらないプログラムになった。**
  引数を読む側の上限は、規模を引数に取る限り要る。
  **2 巡目は上限の根拠そのものを指された。** `Number.isSafeInteger` は `index += 1` が
  終端に届くことしか保証せず、**現実の時間で終わることは保証しない**（100,000 セルで
  約 45 秒、500,000 セルは 3 分で終わらない）。上限は**数として表せるか**ではなく
  **実際に測れるか**で採る（`MAX_CELLS = 100_000`、要件の規模の 10 倍）。
  **3 巡目は「平均依存度 3」の読み違いを指された。** 要件が言うのは**ブック全体**の値だが、
  当初の形（10 列中 3 列が定数）は 2.1 しかなかった。列幅を 100 にして 2.91 に寄せた。
  **さらに 4 巡目で「2.91 では要件を測っていない」と指された。これも正しい。**
  依存度を**一様に保ったまま**では `3(W-3)/W < 3` で届かないが、**揃えることを諦めれば届く**
  ——行の末尾 9 列に 1 本ずつ辺を足せば 30,000 辺ちょうどになる。
  **要件が定めているのは平均であって、各セルが同じ数だけ読むことではない。**
  「構造的に不可能」と書いたのは、一様性を暗黙の前提に置いた誤りだった。
  **しきい値超過時に終了コード 1 を返す経路にもテストが無かった**ので、計測から
  切り離して（`benchResult`）検査できるようにした。**壊れても「速いから緑」で気付けない**

### 段階 7 の計測（Node 22、CI ではない手元の環境）

| シナリオ | フル再計算（N-2、上限 1 秒） | 1 セル変更の増分（N-1、上限 100ms） | 計算し直したセル |
| --- | --- | --- | --- |
| スカラ鎖（100 列 1 行、左 3 つの和。平均依存度 3） | 154ms | 0.70ms | 98 件 |
| 範囲集計（10 セルの窓 + A 列全体の総計） | 94ms | **6.9ms** | 3 件 |

**範囲集計の増分はスカラ鎖の 9 倍。** 計算し直したセルは 3 件しかないのに 98 件のスカラ鎖より
遅いのは、
総計のセルが A 列 9,090 セルを読み直すためで、**段階 6 が懸念していた矩形の費用が
そのまま出ている。** それでも上限に対して 15 倍の余裕がある。

**CI ランナー（ubuntu-latest）では手元より速かった**（フル再計算はスカラ鎖 100ms /
範囲集計 76ms、増分は 0.055ms / 5.7ms）。**絶対しきい値を採る上での唯一の賭けが
「ランナーが遅くて余裕を食い潰す」ことだった**ので、ADR-0025 に数字を残してある。
余裕は N-2 で約 10 倍、N-1 で約 18 倍。

## M3.5 で決めたこと

**3 点を利用者に確認して決め、[ADR-0026](adr/0026-web-ui-stack.md) に書いた。**

- **UI は React。** M3.5 の目的は「UX の前提を早期に検証する」ことなので、
  **M6 で載せ替える前提の構成で検証しても検証にならない。** バンドルは 81KB gzip で、
  要件 N-3（500KB gzip）の 2 割に収まっている
- **DOM を伴うテストは vitest + happy-dom。** TDD が必須である以上 Red を出せる形が要り、
  「DOM に触れない層だけテストする」案は**再計算が画面に出ることをテストの外に落とす**
  ——それは M3.5 の主題そのものである。**環境の指定は設定ファイルではなくファイルの先頭**
  （`// @vitest-environment happy-dom`）に置いた。どのテストがブラウザを前提にしているかが
  ファイルを開けば分かる
- **ビルドは Vite**（ADR-0001 が「`web` を作る段階で足す」としていた）。
  `@sec/core` はソースのまま解決されるので、**core 側にビルド段は要らない**

### 描き直しの粒度を再計算の粒度に合わせた

**`LiveSheet.put` が返す番地だけを描き直す。** 10×10 なら 100 個を毎回読み直しても足りるが、
**それでは増分再計算が働いているかが画面から分からない。** 段階 6 が `put` の戻り値を
「グリッドの描き直しが要る範囲でもある」と書いていた形を、そのまま実装にした。

### グリッドに出す字面は §0.3 の表記と 2 箇所だけ違う

`printValue`（§0.3）はゴールデンテストの期待値の表記で、**値の種別が字面から分かること**が
要る。グリッドはそうではない。

| 値 | §0.3 | グリッド | 理由 |
| --- | --- | --- | --- |
| 空セル（`nil`） | `nil` | 空欄 | 100 個の升目が `nil` で埋まると表として読めない |
| 文字列 | `'abc'` | `abc` | 引用符はゴールデンの表記であって画面の表記ではない |

**値の側は変えていない**（ADR-0010 のまま）。変えたのは見せ方だけで、
`=A1 + 1` が空セルに対して `#TypeError` になることには影響しない。
**配列の要素の文字列は引用符が付いたまま**——外すと `#(a b)` がシンボルの配列と
見分けられなくなる。

### テストの前提が 2 つ誤っていた（実装ではなくテストを直した）

- **`type` ヘルパが既存の内容を消さずに打っていた。** 編集は原文を持った状態で始まるので
  （Excel と同じく数式を直せる形）、`2` の入った升目に `10` と打つと `210` になる。
  **期待値の側は正しかった**ので、ヘルパを「入れ替える」に直した
- **`#Ref` は窓の外を指したから出るのではない。** 出るのは**解決できない番地**
  （`A0`。行は 1 始まり、§4.2）で、**`LiveSheet` に広さの上限は無い。**
  **10×10 はシートの広さではなく窓である。** 窓の外（`ZZ999`）は空のセルとして読めるので、
  `=ZZ999 + 1` は `#Ref` ではなく `#DoesNotUnderstand`（`nil + 1`）になる。
  この決定を固定するケースを足した

### Biome の a11y 規則を 2 箇所だけ抑制した

`noNoninteractiveElementToInteractiveRole` が `<table role="grid">` を拒むが、
**WAI-ARIA はこの形を明示的に認めている**（APG のデータグリッドがこの形）。
規則を全体で切ると他の箇所の保護まで失うので、**理由を添えて 2 箇所だけ抑制した。**
`div` に置き換える案は、行と列の対応を自前で持つことになるので採らなかった。

**抑制のコメントは対象の直前の行に置く。** 理由を複数行に分けると、次の行が
コメントになってしまい `suppressions/unused` になる。

### 残した宿題（M6 で決める）

- **数式バー**（F-7-2）・**範囲選択とキーボード移動**（F-7-1）・**エラーの説明の
  ツールチップ**（F-7-4）は入れていない。M3.5 の範囲として利用者と決めたもの
- **矢印キーで升目を移動できない。** 焦点は Tab で辿れるが、100 個を Tab で辿るのは
  実用的ではない。`role="grid"` を名乗る以上、roving tabindex が要る（M6）
- **IndexedDB への自動保存**（F-5-2）は入れていない。リロードすると消える

### ここまでに分かっている宿題

- **値が変わらなかったセルで下流を止めていない**（段階 6）。今は下流を無条件に辿るので、
  `=A1 * 0` の下流も計算し直される。止めるには**値の比較の意味論**（エラー値や
  ブロックをどう比べるか）を決める必要がある。**段階 7 の計測では要ると分からなかった**
  （上限に対して 15 倍以上の余裕がある）ので、決めるのは要るときでよい
- ~~**マクロ（M4）は 1 回の書き込みごとに再計算を起こす。**~~ → ADR-0027 で
  **書き込みは値を捨てるだけにし、読まれたときと最後に 1 回だけ計算する**と決めた（M4 段階 5）
- ~~**依存の抽出は範囲を知っていなければならない**~~ → 段階 5 で矩形を 1 つの依存として
  扱うようにした。**木から番地を集めれば足りる**という見込みは概ね当たったが、
  **範囲の端が式のときは取りこぼす**（`(A2..A2 detect: ...) to: C4`）。
  取りこぼしを拾うのが遅延の安全網である（ADR-0023）
- ~~**数式セルの値はまだ出せない**~~ → 段階 5 で `recalculate` が `CellValues` を
  差し出すようになった（`values.ts` は `recalc.ts` になった）。**評価器の側は
  セルの解決の時期だけが動いた**（上記）

### 順序の理由

- **本体（段階 1）を先に置く。** 文の列と一時変数が無ければ、ブロック・繰り返し・セルへの代入の
  どのケースも書けない。**段階 1 の 28 件のうち 12 件は構文として拒むケース**で、
  マクロを構文解析器に通すだけで緑になる。
- **非局所リターンを繰り返しと同じ段階に置く。** フィクスチャが `do:` の中から抜けるので、
  `do:` の前には緑にできない。
- **セルへの代入（段階 4）とトランザクション（段階 5）を分ける。** 段階 4 は書き込みを
  `LiveSheet.put` に直接渡せば**下流に届くケースまで緑になる**（今の `put` は下流を
  すぐに計算し直す）。段階 5 は巻き戻しと、`Recalculation.update` を「捨てる」と
  「確定する」に分ける作業で、**ゴールデンテストでは観測できない**（マクロの値しか
  書けない、ADR-0018）ので単体テストで固定する。1 PR 400 行の目安にも収めやすい。
- **ブロックの再帰の 2 件は段階 2 に数えた。** 止まらない再帰の `#Timeout` は、今の安全網
  （`RangeError` を受け止める）で緑になる見込み。**明示的な上限は段階 7** で入れ、そのとき
  上限値も決める（#27）。
- **CLI（段階 8）は完了条件には無い**が、M2 の段階 7 と同じく開発時のフィードバックループの
  基盤になる。M5（MCP）の試し実行（F-6）も同じ入口を使う。

### 段階 0 で決めたこと

**実行の側の 5 論点を利用者に確認して決め、[ADR-0027](adr/0027-macro-execution.md) に書いた。**

- **どの文でも値がエラーになったら、その文の列はそこで打ち切られる。** マクロ本体なら
  マクロがそのエラーで終わる（`1 / 0. ^ 3` → `#DivideByZero`）。ブロック本体なら
  そのエラーがブロックの値になる。**エラーを黙って捨てる経路を作らない**
- **書き込みは同じマクロの中で下流の数式に届く。** 書き込みは下流の値を捨てるだけにし、
  読まれたときに計算する。成功したら残りをまとめて確定し、失敗したら取り消し記録の原文を
  書き戻す。**控えるのは原文**なので、書き込み先の数式もそのまま戻る
- **書き込む値は §0.3 の表記で内容として置く。** 文字列は常に引用符付き（`'3'` は数に
  ならない）、`nil` はセルを空にする。ブロック・範囲・区間は `#TypeError`。
  **エラーを要素に持つ配列も書き込めない**——`#(1.0e400)` の表記 `#(#Overflow)` は
  シンボルの配列として読み戻され、別の値になる
- **時間の上限はホストが掛ける。** `core` はステップ数と再帰深度だけを数え、決定的なまま。
  **ホストには CLI の `sec run`（段階 8）も含む**（AI レビューの指摘）。ホストはマクロを
  隔離した単位で写しに対して動かし、最後まで走ったときだけ反映するので、
  **打ち切っても何も書き込まれず、巻き戻しはそれで成り立つ**
- **マクロから他のマクロを呼ぶ機能（F-3-7）は M4 に入れない。** ただしブロックが一時変数を
  通して自分を呼べるので、**再帰深度の上限は M4 で入れる**

**`macros.txt` を評価の対象に入れた。** `^ 3` を数式として読めば `#Syntax` になる、といった
**数式の側のケースが回帰検査の外に残っていた。** 印の無かった数式のケース 2 件
（`#(1 2 3) do: [...]` と `[true] whileTrue: [1]`）は今の評価器では `#DoesNotUnderstand` で
落ちるので、`!pending m4` を付けた。

### 段階 1 で決めたこと

- **入口は `evaluateMacro(source, cells)`**（`packages/core/src/eval/evaluate.ts`）。
  `evaluateFormula` と同じく**値と診断の組**を返し、構文エラーは `#Syntax` と診断になる。
  読めなかったときの扱いは開始記号で変えない（`parseOrFail` を共有する）
- **ステップ数の予算はマクロ 1 回の実行に 1 つ。** 文ごとに作り直すと、上限に届かない文を
  並べるだけでいくらでも長く走れてしまう。単体テストで固定した
- **一時変数は可変の `Map` で持つ。** 数式の環境（ブロックの引数）は作ったら変わらないので、
  書き換えられる束縛はここだけである。**ブロックが捕まえるのは同じ `Map`** なので、
  外側の一時変数を読むブロックは呼ばれた時点の値を見る
- **セルへの代入は未実装の例外**にした（段階 4）。そのケースには印が残っている

### 段階 1 で印が外れた想定外の 6 件

| ケース | 見込み | 緑になった理由 |
| --- | --- | --- |
| `^ [\| a \| a] value` → `#Syntax` など 3 件 | 段階 2・3 | 構文として拒むだけで、ハーネスがマクロ本体を構文解析器に通せば足りた |
| `^ true whileTrue: [1]` → `#DoesNotUnderstand` | 段階 3 | `Boolean` が `whileTrue:` を理解しないのは今も同じ |
| ブロックの再帰 2 件（`55` と `#Timeout`） | 段階 2 | 一時変数の `Map` をブロックが共有するので自分を呼べる。止まらない方は `RangeError` の安全網（段階 7 で明示的な上限に置き換える） |

### 段階 1 で残した論点は閉じた（ADR-0028）

**一時変数に `Cell` を代入したとき、セルのまま持つ**と利用者と決めた
（[ADR-0028](adr/0028-temporary-holds-cell.md)、仕様書 §7.3）。**値を持たせたいときは
`a := A1 value` と書く。** 段階 1 の実装が既にこの形だったので実装は変えていない。
`assignment.txt` に 6 件足した（印の無い 3 件は緑、書き込みを伴う 3 件は `!pending m4`）。

**段階 5 で閉じた:** `^ a` の `a` がセルで、その値がエラーのときは**失敗として巻き戻す**
（[ADR-0031](adr/0031-macro-result-resolves-cell.md)、利用者の選択）。

### 段階 2 で決めたこと

- **ブロックの一時変数は起動ごとに新しく作る**（[ADR-0029](adr/0029-block-temporaries-per-activation.md)、
  利用者の選択）。再帰の各段が自分の一時変数を持つ。外側の一時変数は共有する
- **束縛の表には値ではなく名前ごとの入れ物（`Binding`）を置く。** 段階 1 の実装は値を直に置いていたので、
  引数を束ねるために表を写すと、**引数を取るブロックからの書き込みが写しに落ちて外側に届かなかった**
  （`[:x | a := x] value: 5` の後も `a` が `nil`）。このケースを固定してある
- **文の列の評価はマクロの本体とブロックで共有する**（`runStatements` は最後の文の値を返す）。
  `^` の扱いだけを呼ぶ側に残した。**ブロックの中の `^` は段階 3 まで未実装の例外**
- 数式のブロックも同じ経路を通る。文が式ちょうど 1 つであることは `parseFormula` が保証するので、
  評価器は開始記号を区別しない

**新しいケースが意味を持つことは変異で確かめた。** 一時変数を本体ごとに共有する変異は
2 件（再帰の `6` と、前の起動の値が残らないケース）で、外側を値で写す変異は 1 件
（引数を取るブロックからの書き込み）で落ちる。

### 段階 3 で決めたこと

- **非局所リターンは例外（`MacroReturn`）で `evaluateMacro` まで飛ばす。** 評価器は
  「エラーは値」の方針だが、打ち切りの印を値に載せると、ブロックを評価するすべての経路
  （条件式・列挙・整列の比較・`whileTrue:`）がその印を素通しする必要があり、
  **1 つ見落とすと `^` の値がただの値として外側の文に続く。** 戻り先は常にいま走っている
  マクロなので（ブロックはセルに書き込めない、ADR-0027）、捕まえる場所は 1 つで足りる。
  数式のブロックには `^` を書けない（§7.7）ので、数式の経路には現れない
- **ブロックの値がエラーなら `^` に達したかを問わずそのまま返す。** エラーはどの経路でも
  打ち切りとして外へ伝わるので、マクロは同じエラーで終わる（ADR-0027）
- **`whileTrue:` は 1 回まわるごとに 1 ステップ払う**（CLAUDE.md 規約 4）。受け手と本体も
  ステップを使うが中身次第なので、ループそのものに上限を掛けた
- **`whileTrue:` は引数の型を受け手のブロックより先に問う**（§5.2 の条件式と同じ）。
  `[1 / 0] whileTrue: 1` は `#TypeError`。受け手の値が `Cell` でも真偽値ではないので
  `#TypeError`（§6.3、ADR-0022）
- **空の受け手への `do:` は引数の数が合わないブロックも問わない**（`#() do: [1]` → `#()`）。
  `collect:` と同じで、要素が無ければブロックを評価しない（§6.3）

単体テストは、**ゴールデンテストの 1 段の `do:` では見えないもの**に絞った。非局所リターンが
入れ子・再帰の内側・`whileTrue:` の本体・`sorted:` の比較（評価器の外の制御）から抜けること。
例外を捕まえない変異では 5 件、`whileTrue:` の受け手を先に評価する変異では 1 件が落ちる。

### 段階 4 で決めたこと

- **配列の要素の `Cell` は値まで解決してから置く**（[ADR-0030](adr/0030-array-cell-elements-on-write.md)、
  利用者の選択）。範囲の列挙が渡すのは `Cell` なので `collect:` の結果はセルを要素に持ちうるが、
  最上位の `Cell` と同じ扱いにそろえた。要素の値がエラーならそのエラーで終わる
- **`evaluateMacro(source, sheet)` はシートを必須で受け取る。** 型は `MacroSheet`
  （`values` と `put`）で、`LiveSheet` がそのまま満たす。書き込み先の無いマクロ実行は
  意味を持たず、**読みと書きを別々に渡せると古い読みと組み合わせられる**
- **評価器の内部で受け渡すものを `CellValues` からシートに替えた。** マクロのブロックも
  文の列を持ち、その中からセルに書き込めるため（§7.5）。数式の評価は書き込めないシート
  （`readOnly`）を使う。数式に代入が現れないことは構文解析器が保証するので、その `put` は
  呼ばれたら例外にする（実装の誤り）
- **値を内容にするのは `write.ts` の `contentToWrite`。** 表記は `printValue` をそのまま使い、
  ここでは「表記してよい値か」だけを決める。表記を 2 つ作ると読み戻しの保証が片方だけ崩れる
- **書き込みは今の `LiveSheet.put` に直接渡す。** `put` は下流をすぐ計算し直すので、
  下流に届くケースはこれで緑になった（段階割りの見込みどおり）。**捨てると確定するの分離、
  巻き戻しは段階 5**
- 書き込み先を解決できない（`A0 := 3`）ときは `#Ref`。読むときと同じ（§4.2）

**置かれた内容の字面と、書き込めない値でセルが書き換わらないことは単体テストで固定した。**
マクロの値には出ないため。`nil` を `'nil'` と置く変異はゴールデンテストでは落ちない
（内容 `nil` も値は `nil` に読み戻される）ので、単体テストだけが捕まえる。

### 段階 5 で決めたこと

- **入口は `LiveSheet.begin()`。** 返すトランザクションは `put` / `commit` / `rollback` を持ち、
  **閉じるのはどちらか 1 回だけ。** 開いている間は `LiveSheet.put` で書けず、重ねて開けない
  ——外から書けると、巻き戻しがその書き込みを知らずに消すか残す
- **`Recalculation.update` を `invalidate`（値を捨てる）と `settle`（まとめて計算する）に分けた。**
  `LiveSheet.put` は両方を続けて呼ぶので、外から見た振る舞いは変わらない
- **`evaluateMacro(source, sheet)` の `sheet` は `TransactionalSheet`（`begin` を持つもの）になった。**
  開いて走らせ、値がエラーなら `rollback`、そうでなければ `commit` する。**評価器の外の例外で
  抜けるときも巻き戻してから投げ直す。** 読めないマクロは開かない
- **マクロの値は閉じる前にセルの値まで解決する**（ADR-0031）。セルのまま返すと、表記するときに
  巻き戻した後のシートを読んでしまう
- **取り消し記録は書き込んだセルの最初の原文だけ**を控える（ADR-0027）。巻き戻しは原文を
  書き戻して捨て、`settle` で計算し直す。値が開始前と同じになることはフル再計算との比較で固定した

### 段階 5 で見つけて直した穴

**読まれたセルだけを計算する（ADR-0027 の案 C）と、長い鎖で再帰が尽きた。** 書き込みで値を
捨てたセルを読むと上流へ潜って評価するので、鎖の長さがそのまま再帰の深さになる。
**1000 段の鎖の根に書いて末端を読むと `#Timeout`** だった（それまでの `put` はトポロジカル順序で
計算していたので起きなかった）。**評価の枠の外からの読みに限り、上流の捨てたままの数式セルを
トポロジカル順序で先に埋める**ようにした。読まれたセルに届かない枝は計算しない（テストで固定）。

**上流は読まれたセルの依存から辿る**（AI レビューの指摘、[#75](https://github.com/kittenkiki15/sec/pull/75)）。
最初の実装は読むたびに捨てたままのセルを全件見ていたので、**独立した枝を順に読むマクロでは
読む回数との積**になった（8000 枝で 5.6 秒）。依存から辿る形にして 71ms になった。
**矩形の依存は小さい方から見る**——中のセルを数え上げるか、捨てたセルが中にあるかを見るか。
振る舞いを変えない性能の修正なので失敗するテストは書けず、**矩形の 2 つの経路を守るテストを
先に足してから**替えた（それぞれ片方だけを壊す変異で落ちる）。
最初は変異を捕まえるために鎖を 5000 段に伸ばしたが、**走査の費用が鎖の長さの 2 乗で嵩み、
カバレッジ計測下の CI で時間切れになった。** 前のセルを読む箇所をブロックの入れ子の奥に置き、
1000 段で尽きるようにした。

**確定の計算が例外で抜けても巻き戻せる**（AI レビューの指摘）。`commit` は計算してから閉じ、
`evaluateMacro` は確定が抜けたら巻き戻して投げ直す。**`rollback` は原文を戻したら閉じる**
——計算が抜けて開いたままだと、そのシートに二度と書けなくなる。`settle` は計算し終えてから
捨てたセルを忘れるので、抜けた後の確定も下流を返し損ねない。

**書き込みは書き換える前に原文を控える**（AI レビューの指摘）。書き換えてから控えると、
無効化の途中で抜けたときに控えが無く、書き込みが残る。**解決できない番地は控えない**
——控えると巻き戻しがそこへ書こうとして抜ける。**巻き戻しも失敗したら、元の失敗と両方を
`AggregateError` で投げる。** どちらか一方だけを投げると、もう一方が黙って消える。
**エラーの値で終わった経路も同じ**で、元の失敗は値なので、その表記を持つ例外にして含める。

**変異で確かめた:** セルを解決しない変異は 4 件、例外で巻き戻さない変異は 1 件、
2 度目の書き込みの前の原文を控える変異は 1 件のテストで落ちる。

### 段階 6 で決めたこと

- **入口は `evaluateMacroDefinition(source, message, sheet)`。** `message` はセレクタと
  **評価済みの引数**（`MacroMessage`）。起動の構文は言語に無い（§7.1）ので、引数を評価するのは
  起動する側（UI・MCP・ゴールデンテスト）である。本体を走らせてからは `evaluateMacro` と
  同じトランザクションを通る（`runInTransaction` を共有する）
- **失敗の順序は §6.0 の送信に揃えた**（[ADR-0032](adr/0032-macro-invocation-arguments.md)、
  利用者の選択）。読めない定義の `#Syntax` → 引数のエラー → パターンと違うセレクタの
  `#DoesNotUnderstand`。**どれもトランザクションを開かない**（単体テストで固定）
- **引数はセルのまま持つ**（ADR-0032、利用者の選択）。一時変数（ADR-0028）と同じ
- **引数は `ReceivedValue` に絞ってから束ねる。** 束縛の入れ物はエラーを持てない型なので、
  エラーの引数を束ねる実装は型検査で落ちる
- **セレクタが合うのに引数の数が違うのは呼ぶ側の誤り**で、例外にする。仕様上の状態ではない
- **ゴールデンテストのハーネスは、`!macro` のメッセージを `nil` を受け手に置いた数式として読む。**
  受け手の無い送信を読む開始記号を `core` に足さずに済む。**引数はマクロが書き込むシートで
  評価する**——セルの値は読み先を捕まえるので（§4.2）、別のシートで評価すると後の書き込みを読めない

**変異で確かめた:** 引数のエラーを見ない変異は 3 件（ゴールデンテスト 2 件と単体テスト 1 件）、
`#DoesNotUnderstand` を引数のエラーより先に出す変異は 1 件、引数を値に解決する変異は 2 件のケースで落ちる。

## 積んであるもの（急がない）

- **リテラル配列の要素がエラーになりうる。** `#(1.0e400)` は `#(#Overflow)` と表記され、
  **エラーを要素に持つ配列**になる（§2.1 が倍精度に収まらない小数を `#Overflow` とし、
  §2.4 のリテラル配列がそれを要素として抱えるため）。**仕様書はこの形に触れていない。**
  段階 6 の実装は、**集計と列挙ではそのエラーを式全体の値にし**（§6.0）、
  **`=` では種別で比べる**（`=` はエラーにならないと §6.3 が定めているため）ことにした。
  **本来は「リテラル配列そのものが `#Overflow` になる」方が筋が良い**かもしれない。
  フィクスチャが 1 件も持たないので先送りした。決めるのは要るときでよい

- **実行上限のうち、ステップ数は入った**（段階 6、`budget.ts`）。
  **残るのは上限値の決定と、時間の次元**（[#27](https://github.com/kittenkiki15/sec/issues/27)）。

  | 次元 | 状態 |
  | --- | --- |
  | ステップ数 | **入った。** 1 ノードの評価が 1 ステップ。列挙は要素の数だけ先に払う |
  | 再帰深度 | `RangeError` を受け止める**安全網**で代替している（明示的な上限ではない）。**M4 の段階 7 で明示的な上限を入れる**（ADR-0027） |
  | 時間 | **`core` には入れない。** ホスト（Web UI・MCP・CLI）が掛ける（ADR-0027） |

  **`STEP_LIMIT` の値（100 万）は暫定である。** §7.8 が「環境によって妥当な値が違う」として
  要件 N-1〜N-3 の性能目標と併せて M4 で決めるとしており、**入れたのは必ず止まることを
  保証する機構であって値ではない。**
  参考: 通る最大の深さは構文解析器が約 4125、評価器まで約 3328（スタック次第で動く）
- **マイルストーンのタグメッセージがタイトル 1 行だけ。** `git tag -n99` で内容を
  見たい場合は、`notes` の入力をタグメッセージにも入れる形にできる。
  ただし `notes` を空にして自動生成させる運用だと、タグメッセージには何も入らない。
  情報は Release に残るため対応は必須ではない
- 要件定義書の未決論点 D-4 / D-5 / D-7 / D-8 / D-9。必要になった段階で決める
