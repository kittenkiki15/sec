# 開発方針

- 版: 1.0
- 最終更新: 2026-09-14

この文書は「1 人の開発者が Claude Code を使ってこの規模の Web アプリを作る」ための進め方を定める。
日々の作業規約は `CLAUDE.md`、決定の記録は `docs/adr/` にある。

## 前提

- 開発者は 1 人。レビュアーはいない。
- 実装の多くを Claude Code が書く。人間はそれを読み、判断する。
- セッションをまたぐと Claude の文脈は消える。**リポジトリに書かれたことだけが記憶として残る。**

この 3 つから方針が決まる。

## 中心となる考え方: 仕様を実行可能にする

この規模で失敗する典型は「AI が大量のコードを生成 → 人間が読み切れない →
動くか分からない塊が積み上がる」。これを防ぐ唯一の方法は、
**Claude が自分で正誤を判定できるループを、実装より先に用意すること**。

そのための仕掛けが `tests/golden/*.txt` のゴールデンテストである。
言語仕様を「式 → 期待値」のテキストとして書き、それがそのままテストになる。

- **Claude が自走できる** — 「`collect:` を実装して」ではなく
  「`tests/golden/collections.txt` を緑にして」と頼める。合否判定を Claude 自身ができる。
- **人間が差分でレビューできる** — 実装 300 行を読むより、フィクスチャ 20 行を読む方が
  仕様の抜けに気づける。
- **仕様書と実装が乖離しない** — 仕様書の各節に対応するフィクスチャがあるかを機械的に確認できる。

言語仕様書（`docs/02-language-spec.md`、M0 で作成）は、**節ごとに対応するフィクスチャ名を明記する。**

## 進め方はテスト駆動開発

上の考え方を日々の作業に落とすと、**テスト駆動開発**になる。
振る舞いを変えるコードは、失敗するテストを書いてから実装する（[ADR-0004](adr/0004-tdd.md)）。

Red（落ちるテストを書き、**落ちることを確認する**）→ Green（通す最小限の実装）→
Refactor（緑のまま整理）。

これは行儀の問題ではなく、この体制における実務上の必要から来ている。

- **実装を先に書くと、テストが「仕様どおりか」ではなく「今の実装がこう振る舞うこと」を
  固定するものになる。** 実装を書いたのが AI なら、その誤りごと固定される。
- **AI に渡す完了条件が明確になる。** 「◯◯を実装して」は判定が人間の目視だが、
  「このテストを緑にして」は Claude 自身が判定できる。
- **レビューの負荷が下がる。** 人間は実装 300 行ではなくテスト 30 行を読んで
  仕様の妥当性を判断できる。

例外（探索的スパイク、ベンチマーク、UI の見た目、機械的リファクタリング、設定・文書）は
ADR-0004 に列挙してある。**それ以外に広げない。**

## フィードバックループは CLI で回す

MCP サーバー（`packages/mcp`）は「エンドユーザーが自然言語でシートを操作する」ための機能であり、
**開発中の Claude のフィードバックループには使わない。** 開発中は CLI の方が速く確実である。

```bash
pnpm sec eval "3 + 4 * 2"           # 式を評価
pnpm sec parse "A1..A10 sum"        # AST を表示
pnpm sec run macro.st --sheet in.json  # マクロ実行（ADR-0034）
pnpm sec bench 10000                # ベンチ
```

Claude Code は Bash でこれを直接叩ける。よって `packages/cli` は M2 と同時に作る。
「動作確認用のおまけ」ではなく開発基盤である。

## 人間と Claude の分担

| 領域 | 担当 |
| --- | --- |
| 言語の構文・意味論の判断 | **人間**。正解が外部にない。AI に決めさせると場当たりになる |
| 受け入れ基準・ゴールデンテストの内容 | **人間**（Claude が叩き台を作る）。ここが仕様そのもの |
| パーサ・評価器の実装 | Claude。ただし**テストを先に書かせ、落ちることを確認させてから**実装させる |
| 組み込みセレクタの網羅実装 | Claude。最も費用対効果が高い |
| エラーメッセージ・i18n 文言 | Claude |
| 依存グラフと増分再計算の設計 | 一緒に。性能と正しさが絡む |
| UI の細部 | Claude |
| **生成されたコードを読むこと** | **人間**。ここを省くと破綻する |

## セッションの運用

- **1 セッション 1 タスク。** 終わったらコミットして `/clear`。長いセッションは文脈が劣化する。
- **着手前に計画を出させ、読んでから実装させる。**
- **1 PR は 400 行以内を目安に。** 読める量しか作らせない。
  ゴールデンテストの追加行はこの勘定から外す。
- **マージ前に `/code-review` を回す。** レビュアーがいない分これが効く。
- **セッションの終わりに次の一歩を残す。** issue か `docs/NEXT.md`。
- **判断は ADR に残す。** 「なぜ `A1..B10` にしたか」が残っていないと、
  次のセッションの Claude が善意で `A1:B10` を提案してくる。

## 品質ゲート

コミット前に `pnpm check`（型検査 → Lint → テスト）。PR では CI が同じものに
カバレッジを加えて実行する。**赤いままマージしない。**

PR には自動レビューが走る（`docs/03-ai-review.md`）。指摘は参考情報であり、
妥当性の判断は人間が行う。

差分からは「テストを先に書いたか」は判定できない。検証できるのは次の 2 点であり、
レビューはこれを見る。

- 振る舞いを変える差分にテストが伴っているか
- テストが実装のスナップショットになっていないか
  （実装を消しても落ちないテスト、境界値・エラーケースの欠落）

そのため、**テストは実装より前のコミットに置く。** 履歴が順序の唯一の証拠になる。

## マイルストーン

| M | 名称 | 完了条件 |
| --- | --- | --- |
| M0 | 言語仕様書の確定 | 文法（EBNF）と組み込みセレクタ一覧が文書化され、対応するフィクスチャ名が決まっている |
| **M0.5** | **リポジトリ基盤** | **ツールチェーン・CI・CLAUDE.md・ADR・セッション開始フック・ゴールデンテストのハーネス（完了）** |
| M1 | 字句解析・構文解析 | 仕様上の全構文をパースでき、構文エラーが位置付きで報告される |
| M2 | 評価器 + CLI | セル参照なしの式が評価でき、`sec eval` で試せる |
| M3 | シートモデルと再計算 | 増分再計算と循環参照検出が動く。`sec bench` でベンチが取れる |
| **M3.5** | **動くデモ** | **10×10 の粗いグリッドに数式が入り、再計算される縦切り** |
| M4 | マクロ | 代入・文列・セル書き込み・トランザクション・実行上限 |
| M5 | MCP サーバー | Claude Code から自然言語でシートを操作できる |
| M6 | Web UI | グリッド編集、数式バー、エラー表示、マクロエディタ |
| M7 | 永続化・入出力 | `.secbook` 保存／読込、CSV 入出力、IndexedDB 自動保存 |

M3.5 は技術的必然ではなく**継続性のために置いている。** M1〜M4 は全てターミナルの中の作業で、
成果が目に見えるまで長い。途中で一度「画面で動く」瞬間を挟むことで、
UX の前提（数式バーに Smalltalk 構文を打つのは実際どう感じるか）も早く検証できる。

## マイルストーンのタグ付け

マイルストーンを完了したら、**注釈付きタグと GitHub Release を作る**（[ADR-0006](adr/0006-milestone-tags.md)）。

- タグ名は `m<マイルストーン番号>`。例: `m0.5` / `m1` / `m3.5`
- 作成は Actions 画面の **Tag milestone** ワークフローから行う
  （タグ名・タイトル・本文・対象コミットを入力する）
- 本文を空にすると、直前のタグ以降の PR から自動生成される

手元の git から直接タグを push する運用は取らない。開発セッションの egress ポリシーが
タグ ref の push を拒否することがあり、実際に M0.5 で当たったため。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 言語仕様の手戻りがパーサ・評価器の全面書き直しを招く | M0 で主要論点を確定。変更は ADR に記録し、**ゴールデンテストを先に直してから**実装を直す |
| 性能要件（N-1 / N-2）が終盤に破綻 | `sec bench` を M3 の時点で作り、CI で回帰を検出する |
| AI 生成コードが読まれないまま積み上がる | PR サイズ上限と `/code-review` の習慣化 |
| スコープが膨らむ | 優先度 S / L の要件には MVP 中は手を出さない。思いついたら issue に積むだけ |
| 未使用の抽象が増える | 2 回目に必要になるまで抽象化しない |

## 規模感

週 10 時間ペースで MVP まで 3〜4 ヶ月、集中できれば 6〜8 週が目安。
難所は M3（依存グラフと増分再計算）と M6（グリッド UI）。
M1〜M2 は仕様さえ固まっていれば速く進む。
